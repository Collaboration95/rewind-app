Product and use cases

Who uses Rewind, the fourteen use cases and how they changed, what is in and out of scope, and the quality attributes we designed for.

The use case numbers UC01 to UC14 come from the report's model packages. Where the older package text disagrees with the current code, this page follows the code and marks the use case as changed.

Actors

Three human roles and four systems that act on Rewind.

The platform operator (the team) is a stakeholder rather than an in-app actor: they use health checks, safe logs and the deployment tooling, not an admin screen. The /admin page was removed.

Group ownerHuman (also a member)Creates the group, issues and revokes invites, sets the weekly prompt and time zone, removes a moment in the group. Gets no early view of media.
MemberHumanSigns in, switches between groups, captures, corrects once, chats, watches and downloads films, sets reminders, reports or blocks other members.

Questions to expect

Why is the cycle clock an actor?
It starts use cases (UC07, UC08, the reminder scan) without a human. In UML it is the trigger for those flows. It is an internal scheduler, not a person; the report draws it as an actor on the system boundary for clarity.
Does the owner have extra powers over media?
Only one: remove a moment from the group, which also returns the author's allowance. The owner cannot see sealed media.

Questions to expect

Why fourteen use cases and not more?
Each one is a goal a user or the clock has, and each has two or more flows. Finer steps (for example 'view chat history') are flows inside a use case, not separate use cases. The course asks for the in-scope cases plus the out-of-scope ones on the diagram.
Which use cases are the most complex?
UC06 (atomic quota with one correction), UC07 and UC08 (clock-driven transition plus a retryable background job), UC12 and UC13 (private media access). These carry the design problems and patterns.
Is the package model out of date?
Partly. UC01 and UC10 changed after it was written. The final report refresh (issue #362) must update those two use cases and add the safety and account-deletion cases.

Main flows of the key use cases

Four use cases that carry most of the design: invite and join, contribute within the allowance, close the cycle and compile the film, and watch the film.

UC03 Join a group. The owner creates an invite; the server stores a short code (six letters or eight letters and digits) with an expiry and a capacity check. The invitee signs in first (a pending invite survives Cognito sign-in), enters the code or opens the link and accepts. The server checks that the invite is unused, unexpired, not revoked, that the group has room and that the person is not already a member, then adds the membership in one transaction. Failures (expired, used, full, duplicate, throttled) never add a member.

UC04 to UC06 Contribute. The member opens capture for the selected group, records a video (up to 15 seconds, with a trim bar) or takes a photo, and picks a retro look. The client asks the server to reserve the contribution: the server checks membership, the open cycle and the remaining allowance of five contributions and 30 seconds in the current 7-day window, and records an expiring upload reservation (15 minutes). On hosted environments the browser then uploads straight to private S3. The server verifies and processes the media in a job. The ledger shows 'queued', 'processing' or 'sealed'. The member may delete one eligible contribution in its original window and submit a replacement. Rejected, failed or retried uploads never use up the allowance twice.

UC07 and UC08 Close the cycle and release the film. The scheduler finds a cycle whose end time has passed, marks it closed, creates the successor cycle and queues a compilation job in one persisted step, so a duplicate tick or a restart replays the same transition instead of repeating it. A worker claims the job, joins the accepted clips in accepted-time order at 720 by 1280, normalises loudness to about -16 LUFS, verifies the output and publishes it. Failures retry with limits. If a cycle has exactly one clip, one eligible clip from the group's archive can be added and labelled. The premiere lasts 24 hours from the actual publication time.

UC12 and UC13 Watch and download. The Archive lists released films, newest first, in pages. To play or download, the client asks the API for a film or clip; the route checks the session, the selected group and the release state, then returns an opaque /media/access/<token> link that is valid for two minutes and tied to that session, group, job and purpose. The media route checks the token again, checks file integrity and streams the bytes. An expired token, another session or a member of another group is denied.

Questions to expect

Walk me through what happens when two members upload at the same moment their allowance runs out.
The reservation is a single atomic database operation against the member's counts and seconds in the window, so one request gets the last slot and the other is refused. That is the core of UC06 and is covered by the contribution policy and ledger tests.
What if the server restarts while a film is compiling?
The job is durable. On restart the stale claim expires and the job is claimed again; output publication is fenced so only the current claim can publish. The transition itself is idempotent.
What does a member see for a sealed contribution?
The kind (photo or video), length, day and a state, plus a Delete button if their one correction is still available. No thumbnail, no player, no path.

Questions to expect

What is architected but not implemented?
Release-environment isolation on managed PostgreSQL with its own Cognito pool is built in Terraform and code, but not complete (#230, #504, #515). We say so rather than present release as live.
Why keep both photo and video?
Photos lower the effort to take part, which is the product's point. A photo is a 3-second segment in the film, so both share the same allowance.

Questions to expect

What is your main security risk?
Private media. We reduce it with short-lived opaque tokens, membership checks, no early access for anyone, and integrity checks. The residual risk is that an authorised member can save and share a downloaded film, which no server control can prevent.
How would you scale Rewind?
Move capability tokens and the realtime hub to shared state (the tokens are in process memory today), run several app instances, and move film compilation to a separate worker pool. The job queue is already durable, so that step is mostly deployment.
Which quality attributes drove the architecture?
Privacy of sealed media and recoverability of the cycle transition. They led to the capability-token design, the durable job queue and the persisted, idempotent transition.
