CI/CD and DevSecOps

Rewind uses protected pull requests, parallel Quality checks and source-bound Docker bundles to move a change from a feature branch to hosted dev, then through reviewed promotion to release.

This page follows the post-refactor source tree and GitHub observations made on 20 October 2026. The course asks the team to explain source and artifact management, demonstrate the pipeline, and discuss technical findings. Read Testing and quality for test design and AWS setup for the deployed services.

One repository, two protected branches

The client, server, tests, deployment scripts and infrastructure change together in Collaboration95/rewind-app.

An issue branch starts from current dev and opens a focused PR back to dev. Separate Git worktrees let parallel tasks use independent branches and working directories while sharing repository history. A worktree is a checkout, not another deployment environment.

Both protected branches require a PR, the up-to-date aggregate Format, lint, typecheck, and test result, and resolved conversations. Protection includes administrators; force pushes and branch deletion are disabled. These settings were read with authenticated gh api repos/Collaboration95/rewind-app/branches/dev/protection and the corresponding main endpoint.

Routine dev PRs need no human approval. The working agreement leaves authentication, private media, database migration, deployment and infrastructure merges to the owner. Batched delivery requires a review-agent pass per PR. A green dev change reaches the release branch through a reviewed PR to main; an urgent main fix returns to dev through a PR.

Questions to expect

Why keep infrastructure and application code together?
A PR can review a server change alongside its tests, Docker packaging and required settings. Commit identity connects the review, checks and release bundle.
Does a green agent review satisfy main approval?
No. Live main protection requires one GitHub approval and approval of the last push. An agent review is additional evidence.

Catch problems before the PR

Git hooks provide quick feedback locally; CI remains the enforced merge boundary.

The hooks live in .githooks/, not .husky/. The package prepare script sets core.hooksPath to .githooks; that setting was also verified in this checkout. Pre-commit runs checks, without automatically rewriting source.

Pre-push compares HEAD with the merge base of origin/dev. A documentation-only result skips its test sequence. The local hook does not run the separate PostgreSQL service lane or the full release browser lane. Hooks can be bypassed with Git options; protected-branch CI cannot.

For an application change, diagnose one focused test and then run npm run test:fast. That builds the server once and runs root, server and Jest suites concurrently with CPU caps. It does not collect the CI coverage reports. Changes to export, routing, PWA or accessibility, and every main promotion, also need the relevant slow, coverage and accessibility checks.

Quality is a dependency graph

The required aggregate is one stable check over separate jobs, so parallel work remains visible and failures cannot hide behind a skipped aggregate.

Quality runs on pushes to dev and main, and PR events opened, synchronize, reopened and ready_for_review, including stacked PRs. A feature-branch push alone does not duplicate the PR run. New runs cancel older runs for the same PR or ref.

The classifier compares exact base/head trees. Only ordinary, non-executable Markdown at allowed documentation paths qualifies for the skip. JSON, HTML, code, symlinks, executable files, missing bases and empty comparisons run the full applicable checks. Both sides of renames and deletions are examined. This site’s JSON content is therefore not a docs-only change under that rule.

The aggregate uses always(): classification must succeed; a code change needs every applicable lane to succeed; a docs-only change needs the expected lanes to be skipped. Its message explicitly says that no application tests ran. The browser lane is required on main pushes and PRs targeting main, and is deliberately skipped on dev.

Jest enforces a 70% global statement threshold. Server coverage is measured separately without a numeric threshold. Frontend summaries and server summaries/raw V8 data retain 14 days. PostgreSQL runs the server suite against another engine; its test count is not another set of unique behaviours.

Questions to expect

Why require one aggregate instead of every job name?
Branch protection keeps a stable context while the workflow can split jobs. The aggregate explicitly validates all required outcomes.
Does docs-only green mean all tests passed?
No. It means the diff met the narrow documentation rule and the expected checks were skipped. The workflow says no application tests ran.
Does dev Quality prove the PWA works in a browser?
No. Its dedicated export/browser lane is skipped. Relevant changes still need local slow checks; main adds the browser lane.

Every repository-owned workflow

There are six workflow files in the inspected tree; Dependabot and GitGuardian are separate integrations.

All six workflows are listed below. Quality and deployment share the same fail-safe classifier. Deployment workflows are triggered by a push and wait internally for that exact commit’s successful branch push Quality run; they do not use a workflow_run trigger.

The database workflow is operational tooling, not an automatic action on each merge. It binds dev to branch dev and release to branch main, selects the matching GitHub environment, and shares that target’s deployment concurrency group.

Security checks cover different failure modes

DevSecOps combines source analysis, dependency checks, image/configuration scans, secret detection and restricted deployment identity.

CodeQL and Release security report independently of aggregate Quality. The live branch protections require only the aggregate context; the production dependency audit is inside it. A green Quality result therefore does not mean every independent security scan was a required merge gate.

GitGuardian is a GitHub App check, not a seventh workflow file. A gh api check-runs query for refactor commit 5ac4e67 showed GitGuardian Security Checks: success from app gitguardian on 20 October. Repository settings also showed GitHub secret scanning, push protection and Dependabot security updates enabled.

GitHub deploy jobs request an OIDC token and exchange it with AWS STS for a one-hour role session. Trust restricts audience, exact repository/environment subject and branch ref. There are separate dev and release deploy roles. This removes stored AWS deploy keys from GitHub; the running Lightsail application separately uses a Terraform-created, environment-scoped IAM user for S3 and pool-scoped Cognito account deletion.

Trivy’s IaC gate accepts only recorded exact findings with an owner, reason and expiry. An exception is a documented risk decision, not a claim that the finding was fixed. The current decisions expire on 31 October 2026.

Questions to expect

What is the difference between SAST and SCA here?
CodeQL analyses source and workflow behaviour. npm audit and Dependabot examine dependency vulnerabilities and propose package updates.
Are all AWS credentials short lived?
GitHub deployment credentials are STS sessions from OIDC. The Lightsail runtime uses dedicated IAM-user keys delivered privately by Terraform; do not confuse these identities.
Is a clean Trivy run proof of no vulnerabilities?
It is evidence for the scanned image/configuration and the configured severity/exception policy. It does not prove the absence of every security defect.

From commit to a healthy image pair

CI builds the runtime and web images once for a deployment bundle; the host verifies and loads them instead of rebuilding source.

For a non-docs merge, the deploy job checks out the event SHA and waits up to 1,500 seconds for that SHA’s successful Quality push run on its own branch. A failed, cancelled or timed-out result refuses deployment. A manual dispatch without a comparison base still needs a qualifying green commit.

deploy/release.py builds a source-bound tar bundle: allowlisted source/operator files, SHA-tagged runtime and web images, manifest, image identities and checksums. The workflow verifies it before transfer and compares its SHA-256 on the host. There is no ECR push/pull stage in this path.

Release security builds its own scan candidates. The deployment workflow builds its bundle separately and does not wait for a Release security result. The source describes revision-bound verification; it does not establish promotion of the exact Trivy-scanned image bytes.

After OIDC authentication, CI requires an already-running host, opens SSH to the runner’s /32 address, obtains temporary Lightsail SSH credentials and pins returned host keys. It transfers the bundle, streams hosted settings from private S3, installs the pair, then closes the temporary SSH rule and removes runner key material. These jobs never apply Terraform or start/stop the host.

Questions to expect

Why ship a bundle instead of building on the server?
The host loads the reviewed commit’s verified image pair. It avoids source/dependency rebuild drift and retains a compatible prior bundle for rollback.
Does CI deploy an arbitrary latest branch head?
No. It builds the triggering event revision and requires that revision’s branch push Quality result.

Promotion, verification and rollback

Release has both branch review and a live environment approval gate; rollback preserves compatibility with stored data and configuration.

Live gh api .../environments/release showed a required reviewer, self-review prevented and a main-only branch policy on 20 October. Dev had no environment protection rules. Although workflow comments describe main review as the human gate, the deployed GitHub settings add this environment approval. Approval waiting time must not be reported as build time.

Host activation checks runtime /health, nginx /api/health, and the actual running runtime/web image IDs and source-revision labels. The workflow then probes http://<host-ip>/api/health from the runner. That is an origin HTTP probe. A separate request through the CloudFront HTTPS URL is needed to verify the public TLS/distribution path; real sign-in, capture and playback remain product checks.

The installer restores the prior image pair when activation fails and compatible recovery succeeds. An explicit release-host.sh rollback stages the retained prior bundle and checks health again. It refuses incompatible configuration or a database schema newer than the target. Rolling back images does not reverse migrations or restore post-cutover data.

For a database rollback, stop writers and reconcile a consistent PostgreSQL-to-SQLite export before switching. An old SQLite snapshot cannot preserve later PostgreSQL writes. AWS backups explains the separate data recovery paths.

Questions to expect

What proves the deployed images are the intended ones?
The bundle checksums are verified, then running container image IDs and revision labels are compared with the loaded candidate pair before activation.
Can rollback always restore service?
No. Schema/configuration changes can make an older image unsafe. Recovery then needs a compatible release or an explicit reconciled data recovery procedure.
Does a health response prove a full user journey?
No. It proves the specific readiness checks answered. Cognito redirects, uploads, film release and playback need separate exercised journeys.

Failures changed the engineering approach

The useful lesson is the failure mechanism and the resulting control, rather than a claim that CI is now infallible.

The 8 October baseline in issue #499 records two first attempts that hung in apt-dependent installation: Playwright/Chromium setup and FFmpeg. Both needed reruns. Their successful second attempts were used for job timing; the long failed attempts were excluded from the reported clean-run wall-time distribution.

The later speedup removed unnecessary setup and split independent work. The workflows still contain apt-dependent steps, so the repository does not establish that package-manager hangs have been eliminated.

A refactor broke a deploy script. The Deploy dev run after the #581 merge failed at "Build the verified release bundle". deploy/release.py read the expected migration versions by parsing server/src/db.ts, and the refactor had moved them to server/src/schema.ts. Quality was green because no check exercised that parse against the real tree. PR #583 pointed the script at schema.ts and added a guard in tests/deploy/release-bundle.test.sh. The next deploys succeeded, and hosted dev health reports PostgreSQL, schema ready, migration version 31. The lesson: a script that parses source files needs a test that fails when the file moves.

Questions to expect

What caused the browser flakiness?
Two workers uploaded for the same member while the server accepted one processing job at a time. A slower CI runner exposed the overlap; the fix serialises those uploads and waits for processing.
Did speeding up CI reduce its assertions?
The documented changes parallelised independent suites, cached browser downloads and removed duplicate setup. Browser coverage remains on the release path; skipped scope is explicit.
What is still unresolved about apt hangs?
Caching reduces browser download work, but system dependencies are still installed. The recorded incidents justify monitoring installation failures; they do not prove a complete fix.
