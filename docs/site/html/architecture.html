Technology and architecture

Rewind combines a browser PWA, a modular Node server, relational metadata and private media storage to turn group contributions into a released film.

This map follows the 20 October 2026 refactor checkout. The code takes precedence over older report models: real accounts are the product, the synthetic Demo is removed, and hosted dev uses PostgreSQL. Deployment diagrams describe the repository configuration; release completion remains tracked separately.

The technology stack

One root package.json declares the client and server dependencies; TypeScript is compiled before the server runs.

The web client is an Expo export built from React Native components. The PWA adds a manifest and a project-owned service worker (no special cases for film or clip paths). It caches the public shell and matching bundles; it does not cache private API/media responses or queue writes while offline.

Questions to expect

Is the PWA a separate application?
No. It installs the Expo web export. The manifest and service worker add browser installation, shell caching and web push.
Does the PWA work fully offline?
The public shell can open offline. Group reads, sign-in, uploads and chat still require the server; private responses and pending writes are not cached.

Logical layers

Presentation, application rules and infrastructure are separate code responsibilities inside one application deployment.

Feature modules share transactions and one release unit. The default CLI starts HTTP, the cycle/media scheduler and configured reminder loop. FFmpeg child processes and the PostgreSQL I/O thread do not turn these modules into independently deployed microservices.

The import guard keeps src/domain and the pure cycle engine free of non-relative imports. It is a focused static rule, not proof that every dependency obeys a strict architectural layer. See design decisions and analysis to design.

Questions to expect

Why call this a modular monolith?
Features are separate TypeScript modules but share one server deployment and relational state. They call functions directly rather than communicating through service APIs.
Where is a rule enforced?
The server is authoritative for membership, quota and publication. Client checks guide the user but do not authorise a request.

Questions to expect

What changed in the HTTP refactor?
The large transport module was split into route tables and shared route helpers. http.ts now composes them; the API remains one server.
Does a report package equal a deployable component?
No. Access, capture, cycle, participation and archive organise the models and explanation. Implementation boundaries are folders and functions within the shared application.

Questions to expect

Is the origin hop encrypted?
The declared CloudFront custom origin is HTTP. The runtime trusts forwarded HTTPS only with the configured origin secret; a forwarded protocol header alone is insufficient.
Are there multiple API replicas?
The default configuration has one runtime. SSE fan-out, media grants, rate buckets and identity caches are process-local; more replicas would need coordination or routing changes.

Request path: upload a contribution

An upload intent reserves allowance before S3 transfer; completion verifies the exact object before registering the contribution.

The runtime paths are POST /real/groups/:groupId/upload-intents, POST .../:intentId/complete and POST .../:intentId/reconcile; the web proxy adds the /api prefix. Reconciliation recovers a transfer whose completion response was lost. Repeating a completed intent returns its existing receipt.

The disk path sends bytes through POST /contributions/upload/source, then registers them through /contributions/upload and processes the clip job. Server probing supplies trusted metadata. The request body, captured dimensions or a client-generated ID never establish ownership by themselves. See database allowance and integrity.

Questions to expect

What if a retry arrives twice?
Intent uniqueness and request hashes distinguish a safe replay from a conflicting request. Completion stores the contribution and job receipt in the same transaction as consumed quota.
Can a successful S3 upload bypass quota?
No. S3 grants byte transfer only. The application rechecks quota, membership, cycle and exact object version before it registers the contribution.

Request path: play a film

The server advertises a short-lived media grant, then rechecks authority and integrity when the player uses it.

The URL contains neither the application session token nor an object-store path. A media element can use the grant without attaching an app cookie; the server still checks the issuing session in SQL. It is a temporary bearer capability and must be treated as private.

The refactor removes legacy direct film/clip download routes. S3 remains private; playback is mediated by the server so revocation, membership changes and output-integrity checks still apply. See the media decision.

Questions to expect

Why not expose a signed S3 GET?
The application wants current session, selected membership and publication checks when bytes are requested. Server-mediated capability resolution keeps those checks together.
What if the server restarts?
The process-local grant map is lost. The client must obtain a new URL; the film and durable metadata remain in storage.

Request path: realtime chat

Messages use HTTP mutations and durable SQL events; server-sent events carry updates to connected members.

This is SSE plus normal HTTP, not a WebSocket service. GET /realtime/groups/:id/messages supplies bounded history; POST on that path sends text. Replies and the supported reaction are separate validated mutations.

The service worker leaves realtime event requests browser-owned so cancellation closes the actual network stream. nginx disables response buffering. Session/group checks also run during stream handling. A SQL event log makes message replay durable, while live subscribers and reaction revisions remain process-local.

Questions to expect

Why persist events if a live stream exists?
The stream can disconnect. Ordered message events let the client resume from a cursor and recover updates it missed.
Are reaction events part of that durable cursor?
No. Reaction rows persist, but live reaction revisions are advisory. Reconnect refreshes reaction counts without advancing the message/unread cursor.

Cross-cutting policy and operations

Every feature shares identity, resource policy, bounded intake and safe operational reporting.

ConcernConcrete implementation
Identity and sessionsCognito code + PKCE exchange produces a Rewind opaque session. Web uses a Secure, HttpOnly, SameSite=Lax __Host cookie; SQL stores its SHA-256 hash. Idle expiry is 7 days; absolute expiry is 30 days.
Resource authorityResolve account and profile from the credential; check accepted membership and selected group. Recheck after asynchronous media work. Request group/member IDs cannot grant authority.
Rate / concurrencyProcess-local token buckets bound chat, group creation and safety actions; persistent login/invite throttles survive restart. Separate intake, processing, Archive and stream limits bound resource use.
Body limitsDefault JSON 64 KiB; upload-intent and reminder registration bodies 8 KiB; staged photos 10 MiB and clips 50 MiB. Timeouts and bounded rejection handling constrain slow intake.
ErrorsResponses use stable error codes with user-facing messages. Hidden/unavailable media gets safe denial/not-found responses; uncaught failures become generic errors with request IDs.
Audit / observationAllowlisted session/job/integrity/repair events persist with result/time and sanitised identifiers. Optional request timing logs route templates and SQL timing; raw query values, tokens and message content are excluded. The actor is the signed-in member’s profile id for real-account actions, and null for system or scheduler actions.
Integrity / recoveryGeneration-fenced durable job claims, pinned object versions, SHA-256/size receipts and schema readiness stop stale work or altered outputs from being treated as ready.

Questions to expect

Does checking membership once cover a long upload?
No. Asynchronous transfer and probing can outlive the original context. Completion and serving recheck current authority before committing or sending bytes.
Does audit record every user action?
No. It records a defined set of session, processing and integrity events. Sanitisation also limits stored identifiers; it is not a complete user-activity ledger.

Client screens, state and API boundary

The real-account shell composes feature hooks and shared UI; server responses remain the authority for private group state.

Navigation is composed from shell tabs and pushed feature/settings state in the group hooks. The current shell tabs are Home, Chat and Archive. Capture and Film are feature views controlled by this composition, rather than independent web applications.

The 20 October refactor extracts hooks and panels from the group, video-capture and settings screens. That reduces the orchestration inside large components while preserving the existing HTTP contracts. See patterns for the design problems behind these boundaries.

Shared codesrc/ui provides tokens, fonts, primitives and icons; src/domain provides typed group/cycle/contribution/film contracts. There is no second synthetic app behind real/.
State and requestsReact hooks/context hold screen and session state. API clients use same-origin /api with browser credentials; retained native development uses a bearer token in SecureStore. postJson shares mutation request formatting.

Questions to expect

What is shared if screens live in real/?
The folder names the real-account UI. Shared domain contracts, UI primitives and capture/chat/reminder adapters live in sibling folders; there is no maintained Demo client.
How do you avoid showing the old group after switching?
Group hooks track context versions and selected-group refs. Late responses from the previous context are discarded, and the server independently checks the selected membership.
