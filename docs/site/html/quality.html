Testing and quality

Rewind is checked by six test layers and four static gates, and every merge to dev has to pass them in CI.

Counts on this page were taken from the post-refactor tree (branch guru/simplify-refactor-20261020, PR #581) on 20 Oct 2026. File counts come from find/ls; test counts and coverage come from the runs recorded in PR #581. The refactor PR was still open when this page was written.

Test layers

Fast logic tests are many and cheap; browser and deploy checks are fewer and slower. Each layer has its own runner and its own CI job.

The frontend suite ran 1,674 tests in PR #581's verification. The PostgreSQL run of the server suite passed 988 tests with 0 failures. The SQLite server count was not re-measured for this page, so it is not quoted.

Questions to expect

Why two test runners (Jest and node:test)?
The client is React Native/Expo, which needs the jest-expo preset and module mocks. The server is plain Node, so the built-in node:test runner needs no extra dependency. Each tool fits its side.
Why are there more server tests than browser tests?
Server tests are fast and deterministic, and the server holds the rules that matter most (privacy, cycles, uploads). Browser tests are slow and flaky by nature, so we keep them for things only a real browser can show: layout, routing, accessibility.
Do tests touch real AWS?
No. S3, Cognito and web push are replaced by protocol fixtures (for example server/tests/helpers/s3-protocol-fixture.mjs). The deploy fixtures are labelled cloud-free in CI.

npm scripts and when to run each

One command (test:fast) is the everyday check; slower ones run only when a change can break what they cover.

test:fast finishes because the three suites run at the same time with buffered output. Passing suites print only their summary; failing ones print in full.

  • AGENTS.md rule: limit focused diagnosis to two attempts per issue, then record the blocker and move on. Never remove assertions.

Questions to expect

Why not run every test on every change?
Browser and end-to-end runs take minutes and need a built web app. We match the check to the change (the verification tiers in AGENTS.md). CI still runs the full set on every PR, so nothing is skipped before merge.
How do you test the PostgreSQL path locally?
make test-postgres starts a RAM-backed Postgres 17 container, creates a throwaway database, runs the whole server suite against it and drops the database.

Static quality gates

Four checks run in CI as a matrix before the tests: Prettier, ESLint, TypeScript and a custom architecture check.

The architecture check is a small script that reads source files and looks at their imports. It enforces two rules.

Domain modules stay framework-free. Files in src/domain/ and the server's server/src/cycles/engine.ts may only import relative modules. Any bare package import (React, Expo, a library) is a violation. This keeps the business rules testable and portable.

Route modules do not touch the device. Files in src/routes/ and any *.route.* file may not import expo-*, react-native* or @react-native/*. Routes talk to adapters, not to device APIs.

The check is itself tested: tests/architecture.test.mjs asserts that the repo is clean and that a planted bad import in a temporary directory is caught.

Questions to expect

Why enforce architecture with a script?
A rule that only lives in a document is broken within weeks. The script turns the layering from the design into a failing CI job, so a violation cannot be merged by accident.
What does the check not cover?
It only checks imports in the listed folders. It does not prove the whole design is layered; the design itself is explained on the architecture page.

TDD and characterisation tests before refactoring

Before the big 20 Oct cleanup we wrote tests that pin current behaviour, then restructured code while they stayed green.

A characterisation test records what the code does now, right or wrong, so a refactor cannot silently change it. PR #581 ("pin behaviour with tests, then simplify") used this method. The tests were committed first, run green against the old code, and kept green through every refactor commit.

Tests added first: server HTTP route contracts (http-route-contract-auth, -media, -real) and six client screen files named *.characterisation.test.tsx (camera capture, video capture, settings, report sheet, group experience, group experience with capture). Media access denials (cross-group, other member, tampered media, sealed archive) were ported to /media/access before the legacy routes were removed.

Then the code changed. server/src/http.ts went from about 4k lines to 235 by moving routes into server/src/routes/. db.ts went from about 2.1k to 776 lines by moving SQLite migrations to schema.ts. VideoCaptureScreen went from about 2k to 285 lines and Settings.tsx from 1.4k to 38 lines.

The new tests also found a real bug: "Try again" after a failed photo capture did nothing. The test failed before the fix and passes after it.

  • Day-to-day, each new feature or fix comes with a focused test written alongside it; the characterisation approach is for restructuring code that already works.
  • PR #581 is open at the time of writing. Check its state before presenting these figures as merged.

Questions to expect

Is this TDD?
Partly. Classic TDD writes the test first for new behaviour. For refactoring, the safe equivalent is characterisation-first: pin the behaviour, then change the structure. We say so plainly rather than claiming strict TDD everywhere.
How did you know the refactor changed nothing?
The pinned tests stayed green after every commit, and the full suites passed at the end: test:fast, test:slow, test:a11y and the PostgreSQL run.
Did the refactor reduce code?
Not overall. Big files were split into focused modules, and about 5.9k lines of tests were added. The point was readability and safety, not line count.

Coverage

Frontend statement coverage is 89.6% and server line coverage about 86%, measured on 20 Oct 2026.

Before the refactor the frontend figures were 87% statements and 90% lines. CI enforces a floor of 70% statements for the frontend (coverageThreshold in jest.config.cjs) and keeps both coverage reports as artifacts. The floor is deliberately lower than the measured value so it catches large drops without blocking small changes.

Questions to expect

Is high coverage the same as good tests?
No. Coverage shows what code ran, not whether assertions are strong. We pair it with behaviour tests for rules that matter (privacy, cycles) and with characterisation tests, and we never remove assertions to make a test pass.
Why is the CI gate 70% if you measure about 90%?
The gate is a safety floor for accidents, not a target. The real number is reported in the coverage artifacts.

Quality attributes and how each is verified

Each attribute maps to a concrete test or measurement you can run.

Performance numbers. The #353 runner (12 Oct 2026 run, local SQLite, one Mac, loopback) targets a p95 of 2 seconds or less for non-media API calls. Its three repetitions measured p95 between about 4 and 9 ms. Film compilation of 25 six-second clips is checked for 720x1280, 30 fps, audio present and loudness between -18 and -14 LUFS. This is a local result only: it is not PostgreSQL, hosted, S3 or device performance, and the document says so itself.

Reliability across two databases. Release still runs SQLite while hosted dev runs PostgreSQL, so the same server tests run on both engines. That is why no SQLite migration was removed in the refactor.

Questions to expect

How do you prove one group cannot see another group's media?
cross-group-access.test.mjs signs in a member of another group and checks every protected category returns a denial with no content, while the owning group can still read it. The media token tests also cover tampered and sealed media.
Is your performance result valid for production?
No, and the document states it. It shows the code is not slow on a laptop. Hosted, PostgreSQL and device performance still need their own measurement.
Does the accessibility test cover everything?
No. Automated Axe scans find a subset of WCAG problems. We also check keyboard tab order and focus visibility, but we have not done a screen-reader audit.

How the tests run in CI

The Quality workflow runs each layer as its own job; the aggregate Quality check must be green and up to date before a PR can merge to dev.

A docs-only change skips most jobs. The full pipeline, security scanning and deploys are explained on the CI/CD page.

Questions to expect

What blocks a merge?
The protected branch needs a pull request, a green and up-to-date aggregate Quality check, and resolved conversations. Routine PRs need no human approval.
What if a test is flaky?
Known flakes are the apt-get step and one Chromium test. We rerun, and we never delete the assertion; a real fix goes in a separate issue.
