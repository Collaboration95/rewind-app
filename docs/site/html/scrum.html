Project conduct

We ran four two-week Sprints (0 to 3), tracked work in GitHub Issues and milestones, and merged small pull requests behind an automatic quality gate.

Figures come from gh (milestones, issues, PRs) read on 20 Oct 2026, from AGENTS.md, and from doc/planning/project-conduct-evidence.md (snapshot 15 Oct). That evidence file states what is not recorded, and so does this page: there are no meeting minutes, no per-member hours and no original Sprint 2 commitment. Do not present the gaps as facts.

Sprints, goals and outcomes

Zero-based Sprint names: Sprint 0 is foundation, Sprint 3 (11 to 24 Oct) is the current one.

The dev branch only exists from Sprint 2, which is why earlier merges went straight to main. In total the repo has 327 issues (319 closed) and 207 merged PRs: 156 to dev, 51 to main, 1 to another branch.

Dates are by UTC merge date. Milestone membership is mutable (issues move between Sprints), so these counts are not a preserved opening commitment. Milestones were also renamed once: older documents call the foundation "Sprint 1" and the hosted Demo "Sprint 2"; that is historical wording, not extra Sprints.

Sprint 1's record is the weakest: the 26 Sep progress report says review-ready, Sprint not closed, hosted acceptance outstanding. Sprint 2 produced an integrated real-account increment but not full release parity or target-device proof.

Scrum events and how we captured them

We held Planning, Daily Scrum, Review and Retrospective, and turned their outcomes into GitHub Issues.

Sprint 0 planned a 90-minute Planning, short weekday or asynchronous updates, refinement, Review and Retrospective timeboxes. The rule in AGENTS.md is: hold the events, and capture resulting work or decisions as GitHub Issues.

What exists on record is the output, not minutes. Issue #25 holds the Sprint 0 walkthrough, #26 reconciles acceptance, and #27 records the retrospective decision. Later decisions are in PRs and in doc/planning/sprints/sprint-3-cognito/design-decisions.md.

Attendance, meeting durations and Daily Scrum logs were not kept. If a lecturer asks for them, say so, and describe the practice rather than inventing dates.

Definition of Done and verification tiers

An issue is Done when four conditions hold, and we check each change in the cheapest environment that really exercises it.

From AGENTS.md, an issue is Done when all four conditions hold:

1. Its core outcome works, checked in the cheapest real environment that exercises it.

2. npm run test:fast passes and the PR's aggregate Quality check is green.

3. Only for an overnight or batched run, or when the owner asks: one review-agent pass is complete and blocking findings are fixed. Other PRs need no review pass.

4. The PR is merged to dev. Then close the issue with a one-line comment linking the PR.

Screenshots, evidence folders, completion notes, repeated rehearsals and independent human acceptance are not required unless the issue itself makes them the deliverable. This replaced earlier role-based gates (operator, verifier, independent acceptance) that slowed work without improving quality.

Questions to expect

Is a merged PR enough to call an issue done?
Only with conditions 1 and 2: the outcome was checked and Quality was green. The merge is the last step, then the issue is closed with a link.
Why is human review optional?
Small PRs, a strict automated gate and an optional review-agent pass catch most defects. Authentication, private media, migrations and infrastructure are different: the owner merges those.

Backlog management

Three things only: a milestone for the Sprint, labels for scope, and a label for work in progress.

GitHub Project boards are no longer maintained. make issues lists the current Sprint's Doing, To do and Done issues. New issues carry a Problem, Expected and How to check, plus labels and a milestone. They carry no estimates, execution contracts or role assignments.

Scope decisions are explicit. Examples: the synthetic Demo was removed on 6 Oct; reminders are web push only; iOS is delivered as a PWA; media is disk locally and s3 hosted. Archived issues record these cuts.

Questions to expect

How do you stop scope creep?
Anything not on the delivery path gets the archived label and is closed. There is also a scope guard: no new infrastructure, CI workflows or tooling unless an mvp issue needs it.
Why did the milestone counts change after the fact?
Milestone membership is mutable and issues moved between Sprints. We treat the counts as outcomes, not as the original commitment.

Agile engineering practices

Small PRs to a protected dev branch, automated checks on every PR, tests before refactors, and AI agents working under the owner's direction.

Branching. Issue branches start from the latest dev and target dev through focused PRs. main is the reviewed release branch, promoted from dev by PR. Several agents work at once, so large tasks use a separate git worktree.

CI. Every PR runs the Quality workflow (see Testing and quality and CI/CD). Every merge to dev deploys to hosted dev automatically.

Refactoring and tests. Characterisation tests come first, as in PR #581. See the testing page.

Pair programming with AI agents. Be factual about this: much of the code was written by AI coding agents (Claude Code and Codex) that the owner directed, with the owner or team reviewing results. The repo has a Claude/Codex working agreement (AGENTS.md, CLAUDE.md), shared skills such as ship-issues, and an optional review-agent pass (make review) used for overnight or batched runs. The team stays accountable for what is merged. Say how you used agents, and what you checked by hand.

  • Per-member contribution cannot be read from commit authorship alone, because agent-assisted commits are made from the owner's account. Use the issue and PR history plus each member's own account.

Questions to expect

Did AI write your code?
A large share, yes. The owner set the scope, directed the agents, and every change passed the same automated gate. We can explain any module we present, which is why each member owns a use case and design problem (see Who owns what).
How do you keep quality with agents writing code?
Tests first for risky changes, the Quality gate on every PR, an architecture check, and an extra review-agent pass for batches. Authentication, private media, migrations and infrastructure are merged by the owner.
