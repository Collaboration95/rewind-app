Submission and presentation

What the course marks, the dates, the 40-minute presentation plan, and an honest checklist of what is ready and what is not.

Sources: the module briefing slides, the presentation guidelines and the report and progress-report templates, as extracted from the course material. The readiness checklist was made by looking at the repository on 20 October 2026, not from memory.

Assessment and thresholds

Presentation 20%, report 80% (5% of that is peer assessment). 50% passes; 60% is needed to stack to the MTech.

A team of ISS lecturers grades the presentation and the report. Peer assessment rewards members who contribute more to meeting the project objectives; it is not a count of hours. Each member must rank the others with unique ranks in the NUS-ISS Peer Grading System by the deadline, or receives zero for that component. Reminders go to NUS email addresses, and not reading them is not an excuse.

Questions to expect

Does the report weigh more than the demo?
Yes: 80% against 20%. But the report is also assessed through what the presentation shows, so the presentation is our one chance to answer questions before the 1 November submission, which should incorporate the remarks gathered.
What effort does the course expect?
About 10 man-days per participant, with groups of five. We are four, so we need to be explicit about the scope we architected versus what we built.

Required deliverables

A working system, the code, the report, pipeline and tests, slides, and the agile and design artefacts.

Two rules are easy to miss. Each member must own at least one use case (class and sequence diagrams for both analysis and design) and at least one design problem solved with a pattern. The report's Project Plan must name who owns which. See Who owns what.

  • A working system and the code base.
  • The project report, following the supplied template.
  • The DevSecOps pipeline and test scripts, with evidence that the pipeline runs.
  • Crisp, readable presentation slides with good flow.
  • Agile artefacts: product backlog, user stories, sprint plans, burn-down charts, sprint reviews and sprint retrospectives.
  • A high-level design specification of the software architecture, in particular the transition strategies from analysis to design.
  • Detailed analysis and design for each use case (or user story) in scope.
  • Detailed discussion of the design problems solved with design patterns.
  • Well-structured source code with unit tests for classes with more complex behaviour.
  • A design of the DevOps pipelines, with appropriate tools and minimal security considerations.

Questions to expect

What must the analysis and design models contain per use case?
One class diagram for the analysis model, one sequence diagram per major flow for analysis, one class diagram for the design model, and one sequence diagram per major flow for design. The design must follow the transition strategies.
What must a design problem contain?
The problem (brute-force design if needed) with class and sequence diagrams, the candidate patterns, the reason for the choice, class and sequence diagrams for the solution, and the implementation decisions. The system must be implemented from the design after the pattern is applied.

The 40-minute presentation plan

Five segments, written as (talk + Q&A) minutes. The total is 40 minutes including Q&A.

Minutes add up as 3 + 3 + 9 + 8 + 17 = 40. The guidelines say the Q&A time is inside the total, so a segment that runs long takes time from its own questions. Each member presents at least one use case in the Architecture and Design segment, which is also where the course requirement for one use case and one pattern per member is visible to the markers.

The presenter split is a suggestion. It follows the ownership split: A access, B capture, C cycle and archive, D participation.

  • Show unique parts. The audience should remember what is distinctive about Rewind: sealed media, the cycle clock, film compilation, short-lived media tokens. Do not spend time on what every solution has.
  • Do not read slides. The audience can read them. Do not use too many slides.
  • Top-down. Requirements, then the high-level design and decisions, then details.
  • Readable from the back of the room. Large fonts; diagrams that need a zoom belong in the report.
  • Keep the time. Rehearse with a stopwatch and cut, rather than speeding up.

What if one member is absent?
Each segment has a named backup. The demo steps are written so any member can drive them; see the Demo script.
How is the demo 13 minutes if the cycle is 28 days?
Local runs use 10-minute cycles (REWIND_REAL_CYCLE_MINUTES). We start a local group before the presentation so its film is released during the talk, and we keep a pre-seeded hosted group with a released film as a second source.

Questions to expect

The guidelines mention auto-scaling. Do you have it?
No. The briefing example says scalability can be dropped for a proof of concept. We chose one host and bounded concurrency with explicit limits and rate limiting, and we say that scaling out would need shared state for the media tokens and the realtime hub.
How do you know it is fast enough?
We set targets in advance (non-media p95 at most 2 seconds; film ready within 10 minutes) and a script checks them. The local result was far inside both. We do not claim hosted performance from a local run.
