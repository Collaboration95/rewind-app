Database design

Relational tables hold identity, membership, cycle state and durable processing receipts, while photo/video bytes stay on disk or in private S3.

This dictionary follows server/src/schema.ts, db.ts, the SQLite baseline and PostgreSQL baseline 030 plus migration 031 in the 20 October 2026 refactor checkout. PK means primary key; FK means an enforced foreign key; U means unique. A logical pointer is explicitly not an FK. Timestamps are stored as ISO-8601 text, and IDs are text unless stated otherwise.

The entity groups

Account authority, shared media actors and cycle processing form the core; reminders and chat attach to the same group context.

The central relationship is real_accounts → real_profiles → real_group_memberships → real_group_metadata → groups → cycles → contributions. Shared profiles supply the actor IDs used by media and chat. The profile bridge is trigger-maintained, not a profile-to-profile FK.

A film is a media_jobs row with kind=film and a cycle FK; a processed contribution uses kind=clip. A web-push subscription is a reminder_destinations row with provider=webpush. The persisted prompt is a cycle column, inherited when the successor is created. See request traces for how these records are used.

Questions to expect

Where are users, films and prompts?
Users are real_accounts with a real_profiles row after onboarding. Films are media_jobs(kind=film); prompts are cycles.prompt. The conceptual names do not all correspond to separate tables.
Why distinguish account ID from member ID?
Account ID identifies the sign-in identity. The public member ID is a real profile ID, mirrored into profiles for shared media/chat references. Composite keys prevent mixing profiles between accounts.

Accounts and group authority

Real-account tables establish identity and membership; shared tables provide the media/group anchors.

Capacity, exactly one effective owner and authority to change a group are application invariants checked in transactions. The role CHECK alone does not enforce one owner. Real-account endpoints use real_group_memberships; the legacy memberships table does not grant access.

Questions to expect

Can a selection point at a group the account never joined?
The composite selection FK requires a matching membership. HTTP policy additionally checks the signed-in account and accepted/selected group.
Does deleting a real profile remove its shared actor?
Yes, through the profile bridge trigger. Dependent shared media/chat rows then follow their own FK deletion rules.
Is the 28-day metadata CHECK the local demo clock?
No. The product metadata stays at 28 days; make run-real supplies shorter actual cycle boundaries for testing. These are distinct stored values.

Cycles, contributions and processing

The relational pipeline separates allowance, contribution identity, processing status and release publication.

The application normally creates one clip job for a contribution, but media_jobs.contribution_id is not unique and contributions.media_job_id is not an FK. media_jobs.source_uri, staged_sources.source_uri and media_metadata.source_uri are logical associations. Stating these limits avoids drawing stronger ER relationships than SQL enforces.

Release publication is separate from job readiness: a verified ready film must also have a published cycle and publication timestamp. Collection rollover creates the successor while the old film can still be processing.

Questions to expect

Why have both contributions and media_jobs?
A contribution is the member’s submitted moment and allowance record. A job tracks processing attempts, output identity and failure; the two have different lifecycles.
Can a ready job be shown before release?
No. The serving policy also requires the cycle’s published release marker and verified matching output.
Are the source URI links foreign keys?
No. Their association is enforced by application ownership, generation and verification checks. The schema alone does not guarantee those links.

Chat, reminders and safety

Durable message cursors and an outbox support reconnect/retry; safety records preserve only the references allowed by deletion policy.

The destination’s account FK and session FK independently prove existence, not that the session belongs to that account. Registration checks that association in code. Outbox generation checks stop an old job from using a replaced destination. The current product enables web push only.

Persistent message events support reconnect replay. Live SSE subscriptions and reaction revision counters are process-local; durable reactions are refreshed through snapshots after reconnect. See chat architecture.

Questions to expect

Why have preferences and destinations separately?
Preferences express the member’s choice for a group. Destinations represent device/session delivery registrations, which can change independently.
Does the outbox guarantee exactly one visible notification?
It deduplicates the member’s weekly scheduled send and bounds retries. Provider/network/device behaviour still prevents a claim of exactly one visible notification.
Why SET NULL on report targets?
A report can remain when its target is deleted. Reporter deletion cascades, while target references can become null rather than blocking cleanup.

Constraints, indexes and transaction boundaries

SQL protects identity and receipt uniqueness; application transactions enforce time, authority and cross-table policy.

Allowance windows are seven days from the cycle start. Each member has up to five contributions and 30 seconds per window; one clip is at most 15 seconds and a photo consumes one slot and three seconds. Smaller configured limits apply. SQL bounds maxima and nonnegative counters, while transactional code checks eligibility and remaining allowance.

Unexpired open/pinned intents hold allowance without incrementing consumed counters. Completion rechecks the exact object and current window, excludes its own hold, and atomically writes quota consumption, contribution, job and completed receipt. Expiring an unfinished intent releases a hold without refunding a consumed counter.

Not every relationship is a foreign key: groups.current_cycle_id, contributions.media_job_id, source URI joins and quota-window start pointers remain logical. SQL also does not enforce one owner, capacity or matching group IDs across every related row. PostgreSQL FKs are DEFERRABLE, initially immediate; SQLite enables foreign_keys and WAL when opening the database.

Questions to expect

Can constraints alone implement quota?
No. Eligibility depends on time, consumed usage, active reservations, replacement rules and authority. A writer transaction checks those together.
Does an index prove the request is fast enough?
No. It supports a known lookup/order. Performance still depends on data size, SQL round trips and measurements; this page does not invent a throughput guarantee.
Why store output hashes in SQL?
They bind a successful processing receipt to exact external bytes. Serving checks the recorded digest/size rather than trusting a path or status alone.

Questions to expect

Are there 31 PostgreSQL SQL files too?
No. PostgreSQL baseline 030 represents the first 30 SQLite changes; 031 adds Cognito. There are two PostgreSQL SQL files now.
Has SQLite migration history already been squashed?
Yes. The 31 SQLite files are now sqlite-baseline.sql. schema.ts keeps the 31 receipts. A fresh database runs the baseline; a database at version 31 opens unchanged; any older or damaged database is refused until upgraded with a release from before the squash (tag pre-migration-squash).
How does a concurrent server and worker avoid migrating twice?
SQLite acquires a writer transaction and rechecks receipt state. PostgreSQL runs migration under the shared advisory writer lock. Both commit receipts with the schema change.

Two engines, one tested persistence surface

The database selector changes the engine while the application keeps prepare/run/get/all/exec calls.

With no REWIND_DATABASE_URL, db.ts opens node:sqlite using busy timeout, foreign keys and WAL. Hosted configuration selects PostgreSQL 17. PostgresDatabase sends SQL to a worker thread holding a pg client, then waits synchronously. The translator maps the supported SQL subset and the bridge maps row/error/transaction behaviour.

Every write uses an advisory writer fence to preserve the SQLite concurrency model. Statement savepoints keep a failed statement from poisoning its containing PostgreSQL transaction. Text uses byte-order collation; fractional duration/usage columns use DOUBLE PRECISION and integral columns use BIGINT. This is a compatibility choice, not a claim of using PostgreSQL’s full row-level concurrency.

A remote hosted connection verifies TLS with the bundled RDS CA and persists dev/release binding. The checked-in dev setting enables PostgreSQL cutover; release provisioning is enabled but cutover is false. #504 remains the release persistence task. See the database decision.

Data lifecycle, media keys and deletion

Metadata cleanup and external byte cleanup are separate operations; group films can outlive an individual contribution.

Media keys are environment/groupId/prefix/name, with prefixes incoming, processed or films and a fresh object name for each stored object. Encoded references include backend/store, environment/group, key, exact versionId, SHA-256, byte length, content type and incoming expiry. The adapter authorises scope independently of the reference and deletes an exact version.

Deleting a membership row would cascade its selection, reminder preference and outbox references. Contributions and messages point to shared profiles/cycles/groups, so a membership deletion FK alone would not erase those rows. The current account-deletion workflow is the implemented removal path, not an invented leave-group workflow.

SQL stores receipts and references, not media payloads. A database backup cannot replace an S3/media backup, and a successful metadata transaction cannot prove bytes exist. Publication and serving verify output integrity. Terraform enables S3 versioning, blocked public access and SSE-S3; PostgreSQL import/export tools reconcile counts and table content before accepting a transfer.

Questions to expect

Does account deletion erase every appearance in a group film?
No. Existing group films are retained, with segment timing preserved. Own contribution rows and clip access are removed; best-effort external cleanup is not transactional erasure of every copy.
Why not delete media inside the SQL transaction?
SQL cannot atomically commit an S3/file deletion. The code commits authority/reference changes first and removes owned bytes afterwards; missed cleanup does not restore application access.
Can a media reference from another group be used directly?
No. The adapter checks the authorised environment/group scope, store, exact version and integrity metadata. Knowing a key or reference does not establish membership.
Do films expire after seven days?
No. The declared seven-day rule applies to incoming-tagged objects. Published films use fresh film keys; the inspected configuration has no blanket current-film expiry.
