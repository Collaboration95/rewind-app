Analysis to design

Six transition strategies turn Rewind’s boundary, control and entity analysis objects into concrete client modules, server operations and durable records.

The course template asks for the objects and use cases affected by each strategy, the static changes to a class diagram, and the dynamic changes to a sequence diagram, with reasons for both. The sections below provide that guidance; the model registers link every existing use-case class view and major-flow sequence pair.

This page checks the report models against the current refactor tree. Existing SVGs are earlier report snapshots: Demo lanes have been removed from the product, Cognito and PostgreSQL are implemented, routes live in server/src/routes/, migrations live in server/src/schema.ts, and screens have been split. The SVGs are linked for study and remain unchanged; the current mappings below explain how to read their older names. See ownership and pattern decisions.

From responsibilities to implementation

Analysis identifies who interacts, who coordinates and what the system remembers; design assigns those responsibilities to real code and storage.

A boundary receives an actor’s input or presents a result: sign-in, camera, chat and Archive screens. A control coordinates a use case: authenticate, accept an invitation, reserve allowance or compile a film. An entity carries a domain fact: Account, Membership, Contribution, Cycle, Film or Message.

A design class diagram can represent a TypeScript interface, a class, a React component, a module of functions or a persisted record. Give it the actual implementation name and its kind. Do not turn every analysis noun into a new class: acceptRealGroupInvite and advanceCycleLifecycleVerified are functions, while MediaCapabilities and RealtimeHub are classes.

Questions to expect

Is an analysis control necessarily a design class?
No. It is a responsibility. A function, hook or module can implement it; the diagram should label the actual kind.
What must a design sequence add?
Concrete participants, credentials, validation order, transaction boundaries, asynchronous work and relevant failure branches.

T1 · Establish trusted identity before group access

Refine Account and Membership into verified sessions and explicit account-to-group checks.

Analysis objects impacted: the sign-in and group boundaries; authentication, group-selection and invitation controls; Account, Session, Group, Invitation and Membership entities. Use cases: UC01–UC03 directly, and the protected member flows in UC04–UC06 and UC09–UC14. UC07–UC08 are server-driven work rather than browser sign-in flows.

Static change and rationale: introduce RealAccountProvider, RealAccountClient, the CognitoService contract, auth routes, session records and real membership records. Keep account ID separate from a member’s group profile ID. Both Cognito and enabled developer password sign-in create Rewind sessions; neither bypasses group membership. This lets sign-in transport change without making resource IDs into credentials.

Dynamic change and rationale: for web sign-in, redirect through Cognito with state, nonce and PKCE; exchange the code and verify identity on the server; then issue an HttpOnly Rewind session cookie. Protected routes validate the session before resolving membership or ownership. Invitation acceptance checks expiry, replay, requested group and capacity in its membership transaction. Failures must return before the protected mutation.

Current-code correction: the old ACCESS figures show Demo policy and a future Cognito box. Demo authority is removed. server/src/policy.ts now defines the shared safe-denial value; it is not a universal Strategy implementation. Auth handlers are in auth-routes.ts, real groups in real-routes.ts, and selected-group media identity in media-access.ts.

Questions to expect

Why have a Rewind session after Cognito sign-in?
Cognito verifies identity. Rewind issues its own session and uses its own membership records to authorise group operations.
Does knowing a group ID grant access?
No. The server resolves the signed-in account and checks the applicable membership, selected group and owner rules.
Where is the Strategy class from the old report?
There is no universal policy Strategy class in current code. The implementation uses sign-in adapters and explicit authorisation functions and queries.

T2 · Isolate capture and own local media

Refine a conceptual Recording into camera contracts, recording/review sessions and an explicit file lifetime.

Analysis objects impacted: camera and review boundaries; capture/review controls; Recording, Photo, Trim and pending-media entities. Use cases: UC04 video and UC05 photo; UC06 correction also needs cleanup of replaced or discarded local media.

Static change and rationale: introduce CameraPlatform, ExpoCameraPlatform, BoundedVideoRecordingSession, ClipReviewSession, managed file stores and StillImageCaptureSession. The video screen delegates access, recording, review, upload and cleanup to hooks such as useVideoAccess, useClipReviewState, useClipUpload and useCaptureLifecycle. These seams keep device APIs and media lifetime out of one large screen.

Dynamic change and rationale: obtain permission, capture into an owned local handle, review and trim, then prepare the upload. On web, the photo path applies a retro look before upload; video does so when the browser supports re-encoding. An incapable video browser uploads the original for the server’s look processing. Successful submission, retake, cancellation and interruption must clean up the correct media and ignore late asynchronous completions.

Current-code correction: the older capture models predate the browser retro pipeline and split video hooks. retro-browser.ts and retro-looks.ts now implement the on-device look; clientProcessed tells the worker to normalise without applying the look twice. Native adapters remain in source, while the delivered iOS experience is the PWA.

Questions to expect

Why separate local capture from uploading?
A user can review, retake or lose the network before the server accepts anything. Local media needs its own lifetime and error handling.
Is the look always applied before upload?
Web photos use the browser pipeline; web video uses it when re-encoding is supported. Otherwise video processing falls back to the server.
Is Template Method used here?
No shared base class defines overridable capture steps. The implementation uses contracts, sessions, hooks and explicit async functions.

T3 · Accept contributions atomically and retry safely

Refine Allowance and Correction into persisted quota, contribution, job and replacement records.

Analysis objects impacted: submit/status boundaries; contribution and correction controls; Allowance, Contribution, ProcessingJob and Replacement entities. Use cases: UC04–UC06 directly; UC08 consumes the accepted contributions when building a film.

Static change and rationale: add contribution quota windows, a durable contribution ledger, media-job records, idempotency keys and an explicit replacement link. The server owns both count and duration allowance. A job’s processing state is separate from the fact that a contribution has been accepted, so a processing retry need not consume a second allowance.

Dynamic change and rationale: authenticate and validate the source; check the collecting cycle and reserve both quota dimensions in the acceptance transaction; persist the contribution and job; then process outside the transaction. Replaying the same key resolves the existing result, while a conflicting payload is rejected. This handles a response lost after the server committed.

For correction, check ownership, the current allowance window and the remaining delete entitlement; tombstone the contribution and restore allowance transactionally. Link an accepted replacement to that deleted record. Cleanup follows the committed decision. The UI cannot grant a second correction by deleting its own local state.

Questions to expect

Why is a disabled Upload button insufficient?
Two requests can arrive together or a client can bypass the UI. Only the server’s atomic quota update protects the limit.
What if the upload response is lost?
Retry with the same idempotency key and reconcile the existing contribution. Do not create a fresh key for work the server may already have accepted.
Why preserve a deleted record?
The tombstone and replacement link retain correction history and prevent repeated replacement claims.

T4 · Persist cycle transitions and recoverable film work

Refine Cycle and Film into stored state transitions, successor links, durable jobs and fenced worker claims.

Analysis objects impacted: clock/worker and premiere boundaries; rollover, compilation and release controls; Cycle, Film, CompilationInput and Release entities. Use cases: UC07 and UC08 directly; the result gates UC04–UC06 intake and UC12–UC13 delivery.

Static change and rationale: store cycle status, lock state, transition receipts, successor identity, release status and publication time. Store film jobs, ordered inputs, attempts, lease times and claim generations. These are distinct records because closing intake, running FFmpeg and publishing a film have different failure and recovery points.

Dynamic change and rationale: the scheduler discovers due work; a transaction moves a collecting cycle to revealing, ensures its film job and successor, and conditionally advances the group pointer. The worker claims durable work and performs expensive processing outside that transaction. Only the current generation can finalise verified output. Duplicate ticks and restarted processes reuse persisted intent.

Publication is a separate guarded operation after the cycle end and verified ready output. The premiere lasts 24 hours from release_published_at, so a delayed compilation does not shorten it. Afterwards the old cycle becomes archived while its successor can already be collecting. The current database adapter supports local SQLite and configured PostgreSQL; the old model’s SQLite label is not the whole current deployment design.

Questions to expect

Why does polling not solve duplicate rollover?
Polling only wakes the process. Transactions, transition uniqueness, successor identity and guarded pointer updates make replay safe.
What stops a stale worker publishing?
Finalisation checks the persisted claim generation. A worker holding an older generation cannot complete over a newer claim.
Does the premiere start at scheduled cycle end?
It starts at publication. A late film still receives the configured 24-hour premiere.

T5 · Separate durable participation from live delivery

Refine Conversation and Reminder into committed chat events, reconnect cursors and consent-scoped reminder jobs.

Analysis objects impacted: settings, chat and notification boundaries; prompt, conversation and reminder controls; Prompt, Timezone, Message, ReminderPreference, Destination and Outbox entities. Use cases: UC09–UC11; the older UC02 settings subflows overlap these responsibilities, while Member D owns their detailed explanation.

Static change and rationale: split chat persistence from RealtimeHub and the SSE client. Split reminder preferences and device destinations from outbox records and the provider interface. A chat subscriber exists only while connected; a reminder job must survive disconnection and respect later consent changes. One generic observer cannot express both lifetimes.

Dynamic change and rationale: commit the chat message and event before fan-out. On reconnect, subscribe and buffer live traffic while replaying persisted message events to a watermark, then flush newer events. The stream rechecks access. Reactions use separate updates and do not advance the persisted message cursor.

For reminders, calculate due time in the group timezone, enqueue idempotently, lease a row, recheck session/preference/destination generation, call the provider outside the database transaction, and fence completion by lease. Provider acceptance is not proof of on-screen display. The runtime now starts a non-overlapping reminder loop when providers are configured; the old report’s one-shot-only description is outdated. Web push is the product channel; disabled Expo/native paths in source are not delivered scope.

Questions to expect

Can a pub/sub hub recover a missed message by itself?
No. Rewind replays persisted message events from the cursor. The hub only fans out committed events in the running process.
Are reactions part of the same durable cursor?
No. Reaction frames do not move the message reconnect cursor; the client has separate reaction synchronisation.
Why keep a durable outbox if web push already queues a send?
The outbox records scheduling, eligibility, retries and outcomes in Rewind. It also lets the server cancel stale work after consent or destination changes.

T6 · Authorise each delivery and keep caches public

Refine ReleasedMedia into short-lived access grants, verified serving and client playback/download adapters.

Analysis objects impacted: Archive, player, download, install and invite-link boundaries; release-access and delivery controls; ReleasedFilm, OwnClip, Capability and InviteIntent entities. Use cases: UC12–UC14; UC03 remains the authoritative invitation acceptance operation.

Static change and rationale: introduce MediaCapabilities, media-access routes, verified store-serving helpers, the archive client Facade and download Adapter functions. A capability binds a session, account, group, member, purpose, job and exact output identity. A stored media reference names bytes; it is not membership authority.

Dynamic change and rationale: fetch current archive/premiere state and obtain a fresh grant for the action. Resolve the grant against current session, selected membership, published release and ready output; verify storage bytes and recheck before delivery. Own-clip grants also bind the member who contributed. Expiry or a group/session change forces refresh rather than replaying a stale URL.

Install/update sequences keep a separate public-shell cache: warm the complete versioned shell before activation and bypass API/private media. An offline shell does not make private archive playback available. Invitation links parse into bounded intent; authentication and server acceptance still create membership. Current screens are src/real/Archive.tsx and src/real/Film.tsx, replacing the older Archive-screen name.

Questions to expect

Is a capability a permanent public media URL?
No. It is short-lived and tied to current session, membership, release, purpose and output identity; the serving path rechecks it.
Why refresh just before downloading?
A previously listed URL can expire or lose authority after sign-out, group selection or release changes.
Does offline PWA support mean offline films?
No. The service worker caches the public shell and bypasses private API and media requests.
