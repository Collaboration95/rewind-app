Demo script

A 13-minute demo plus 4 minutes of questions, on hosted dev with a local run as backup, with who drives, what to click, what to say, what to expect and what to do if it fails.

The older demo script (doc/planning/report/presentation/demo-script.md) was written for the Sprint 2 pilot and a headless Firefox test run. It is out of date: the Demo was removed, Cognito arrived, and hosted dev now uses PostgreSQL. This script uses the app as it is today.

Two facts shape the plan. First, a real cycle is 28 days, so a new film cannot be created live on hosted dev unless the host overrides the cycle length. We therefore show a pre-seeded released film on hosted dev, and a live rollover on a local run with 10-minute cycles. Second, the camera needs HTTPS on a phone, so phone capture is done on hosted dev; the laptop can use localhost.

The 13 minutes at a glance

Eight steps, four drivers. Each step shows one use case and one quality attribute.

Member A also acts as the narrator who keeps time and tells the room what is about to happen. The course guidelines ask to demonstrate significant use cases and some important quality attributes such as performance (scripted) and maintainability (run the pipeline). Scalability is not claimed; see Submission and presentation.

Questions to expect

Why not demonstrate everything live?
Thirteen minutes is short, and a 28-day cycle cannot be shown live. We pick the flows that carry the design (sealed contributions, cycle rollover, private media) and show the rest through tests and the pipeline.

Questions to expect

Why can't I see my own clip while it is sealed?
By design. Seeing it would invite re-takes and editing for an audience. The server whitelists metadata and gives no thumbnail or path.
What happens if the upload fails halfway?
The reservation expires after 15 minutes and the allowance is not consumed until the contribution is accepted. The ledger shows the failed state with a retry.

Questions to expect

Why capability tokens instead of signed S3 URLs for playback?
The server must check membership and release state on every access, verify file integrity and apply a serving budget. A short opaque token keeps that logic in one place and keeps object paths hidden. Uploads use presigned URLs because there the server has already checked the reservation.
What if the server restarts during the two minutes?
Tokens are in memory, so they are lost and the client simply asks for a new one. That is safe, but it means the design does not scale across several instances without shared state.

Questions to expect

Can you show auto-scaling?
No. Rewind runs on one host by design. We show bounded concurrency and rate limits instead and say what we would change to scale (shared state for tokens and realtime, a separate worker pool for film jobs).
Is the performance run realistic?
It is a fixed, repeatable workload with declared boundaries. It uses real FFmpeg compilation and real HTTP, but local SQLite and one machine. It catches regressions; it is not a capacity test.

Fallbacks and rules

Decide the order of fallbacks before you start, and never improvise a deploy on stage.

  • First fallback: the local run. make run starts the server with SQLite in .local-data/real and the web app on http://localhost:8090. Sign in with Developer sign-in. Plain HTTP works on localhost only, so use a browser on the same laptop, not the phone.
  • Second fallback: recordings. One short screen capture per step, recorded during the rehearsal. Say clearly that it is a recording.
  • Third fallback: tests. For security and film behaviour run one focused test: npm run test:focused -- server server/tests/media-token-http-contract.test.mjs. Do not run the whole suite on stage.
  • Never merge, push, deploy, change the cycle length of the host or send a push notification during the demo.
  • Camera fails. Use the gallery fallback for video or play the recording; say so.
  • Hosted dev is slow or down. Switch to the local run at once and say why. Do not debug on stage.
  • Time is short. Drop 3b, 8b and the chat reaction first. Never drop step 5 or step 8a.

Questions to expect

What do you say if a step fails on stage?
Name it in one sentence, switch to the fallback and carry on: 'The venue network is slow, so here is the same step on the local run.' Questions about the failure are better answered in the Q&A than during the demo.
What are the first questions in the 4-minute Q&A?
Likely: why sealed media; how you keep media private; what happens if the film job fails; why one host; what changed after the Demo was removed; how each member's work shows in the repository. Each has a model answer on the Product, Architecture, Decisions and Owners pages.
