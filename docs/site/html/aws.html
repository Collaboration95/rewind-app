AWS setup

Rewind runs independent dev and release environments on Lightsail, with CloudFront HTTPS, private S3 media, Cognito sign-in and separately managed PostgreSQL databases.

This page combines the post-refactor Terraform/deployment source with read-only observations on 20 October 2026. Resource existence, application readiness and completed data cutover are different facts. The historical demo infrastructure name means hosted dev for the real-account product; it does not mean a synthetic demonstration app. See CI/CD and DevSecOps for the full check graph.

Terraform owns infrastructure; CI installs the app

Four Terraform roots separate state, dev infrastructure, dev services and release infrastructure.

The S3 backend examples use rewind-terraform-state-330599756236, encryption and native S3 lockfiles (use_lockfile=true). Each root has its own key. Bootstrap declares private, AES256-encrypted, versioned state; superseded state versions expire after 90 days. State and private variable/backend files are not source artifacts and were not read for this inspection.

The dependency order is bootstrap, then the host/deploy role, then environment services. media/ is the direct dev root and a reusable module called by release/ with environment=release. The post-refactor tree removed an unapplied second media path; it is not another live environment.

An operator initialises the backend and reviews terraform plan with the dedicated apply profile before a human-approved apply. Terraform creates cloud resources and sensitive settings; cloud-init installs host prerequisites. GitHub deployment never runs Terraform. Keep infrastructure recovery, application installation and database/media recovery separate.

The demo root and state key are deliberately preserved. Its first-boot script is reused for release. Existing hosts ignore user_data drift so a script edit does not accidentally replace the server; new/rebuilt hosts use the current script.

Questions to expect

Why are there several state keys?
They provide independent change/recovery boundaries. A release plan should not silently take ownership of the existing dev host or its state.
Does merging Terraform automatically apply it?
No. Source checks and IaC scans run in CI, but application deployment does not invoke Terraform. Infrastructure applies remain reviewed operator actions.

CloudFront fronts a small container host

The application compute is Lightsail with Docker Compose; CloudFront terminates public TLS and nginx serves the PWA and proxies the API.

There is no standalone EC2 instance resource, ECS cluster, load balancer, NAT gateway or ECR registry in these Terraform roots. The origin’s generated hostname starts with ec2-, but the managed compute resource is a Lightsail instance. The database resource is aws_lightsail_database, not RDS.

Each environment declares a separate CloudFront distribution using the AWS-provided domain/certificate, redirecting viewers to HTTPS. There is no Route 53 zone or custom-domain certificate declared in this path. Origin traffic is HTTP on port 80. CloudFront adds a secret origin header and forwarded HTTPS indication; the server checks these before trusting the forwarded scheme for protected routes. This is an application trust control, not TLS encryption to the origin.

The web container runs nginx, not Caddy. It serves the Expo export, falls back to index.html for SPA routes and strips /api before proxying to Node. Node owns API handling, the cycle scheduler, media workers and reminders. The runtime port is published only on host loopback; nginx is exposed on port 80 for CloudFront. Both containers have read-only filesystems, dropped capabilities and no-new-privileges; data/staging use explicit persistent mounts.

Questions to expect

Where is HTTPS terminated?
At CloudFront using its default certificate. The declared origin hop is HTTP; do not describe it as encrypted end to end.
Why two containers on one host?
nginx serves static assets and proxies the API; Node runs the application and workers. They can be versioned as a pair without operating a cluster.
Are private APIs cached at CloudFront?
The declared distribution uses managed caching-disabled policies. nginx also sets API responses to no-store.

Private S3 is storage, not a public media website

Media buckets are separated by environment, blocked from public access, encrypted and versioned.

Read-only S3 metadata confirmed versioning enabled and all four public-access-block flags true for both rewind-dev-media-330599756236 and rewind-release-media-330599756236. Terraform additionally declares bucket-owner-enforced ownership, AES256 server-side encryption and a bucket-policy denial for insecure transport.

The server authorises an upload and issues a short-lived signed PUT URL. CORS permits configured app origins and the local test origin for dev; CORS does not grant access by itself. The runtime IAM user is scoped to that environment’s bucket, plus its specific backup prefix and Cognito pool operation.

Archive reads pass through application authorisation: current session, selected group, membership, release state and media integrity. The database pins an exact object version. Random object keys and exact-version deletion keep active Archive references from becoming superseded versions. This is different from serving a public S3 URL.

Lifecycle rules expire abandoned incoming objects after seven days, noncurrent versions after 30 days, and incomplete multipart uploads after one day. Permanent current Archive objects have no age-based expiry in this policy. Local development uses disk storage; hosted media uses S3.

Questions to expect

Why use signed uploads?
The browser sends bytes directly to S3 after server authorisation. It receives a bounded upload capability, not the runtime’s AWS keys.
Does encryption replace member authorisation?
No. Encryption protects stored bytes. The server still checks the signed-in account, selected group and permitted media state on access.
Will a film disappear after 30 days?
The rule applies to noncurrent versions. Active films use random keys and pinned current versions; current Archive objects are not expired just for age.

Managed PostgreSQL trades low cost for availability limits

Dev is deliberately public and single-AZ; release is declared private and also single-AZ.

The source configures PostgreSQL 17 on Lightsail bundle micro_2_0. Dev has enabled=true, cutover=true, public=true; release has enabled=true, cutover=false, public=false. The live databases matched the public/private split and used engine 17.11. Database existence and the selected runtime engine must be checked separately.

Dev is public so the team can browse its data with a PostgreSQL client using the generated read-only login. Public reachability still requires database credentials; hosted connections use certificate-verified TLS. It is not a multi-tenant production network design. Release’s private setting limits network reachability to Lightsail resources in-region; credentials and application environment binding still matter.

A standby was explicitly declined by the owner in closed issue #503 on 7 October. The chosen recovery mechanism is managed point-in-time restore; micro_ha_2_0 remains a configuration option. A restore mechanism is not automatic failover or zero downtime. The single-instance choice keeps this educational deployment small.

The generated admin login is used for role bootstrap. The app and read-only logins have separate purposes. Switching REWIND_DATABASE_URL selects PostgreSQL; an empty setting selects SQLite. Release import/reconciliation must finish before its cutover flag changes. After new PostgreSQL writes, returning to SQLite needs the reconciled reverse export, not a stale file.

Questions to expect

Why no HA standby?
The owner chose a single instance with managed point-in-time recovery for this project. It reduces standing resources but accepts recovery time during a database failure.
Is public dev PostgreSQL unauthenticated?
No. It is network-reachable, but logins are generated and the application uses verified TLS. The public setting exists for team client access.
Why not flip release cutover as soon as the database exists?
Retained data and stopped-writer reconciliation must establish which database is authoritative. Provisioning alone does not move or validate data.

Cognito signs users in; web push sends reminders

Identity and reminder delivery use separate protocols and credentials.

Terraform declares one Cognito Essentials user pool per environment: rewind-dev and rewind-release. Each has a public web client without a client secret, a default Cognito prefix domain and Managed Login v2 branding. Email is the sign-in attribute; self sign-up and email verification are enabled. MFA, social identity providers and a custom domain are not configured.

Web/PWA sign-in uses an authorisation code with PKCE. The server exchanges the code, validates the provider response and issues a Rewind session. Callback/logout URLs derive from the environment’s web origins. Release sets REWIND_AUTH_PASSWORD=false; dev retains Developer sign-in for tests. Cognito inventory was denied to the read-only profile, so these pool/client details are source-verified, not a live pool census.

Cognito is configured with email_sending_account=COGNITO_DEFAULT. There is no application-managed SES identity or SES sending configuration in these Terraform roots. Do not draw SES as a reminder service: reminders use browser web push, including an installed iPhone Home Screen PWA.

The deploy configuration generates a P-256 VAPID key pair once on the host when needed and retains it privately. Terraform supplies the contact subject. The server’s reminder outbox sends through web-push provider endpoints. VAPID identifies the sender; it is unrelated to Cognito tokens or GitHub OIDC. Expo/native push remains disabled.

Terraform settings reach the host through private S3

The implemented configuration path uses encrypted S3 objects and allowlisted host settings, not SSM Parameter Store or Secrets Manager.

Terraform creates the environment’s runtime IAM access key, generated database logins and Cognito settings. It writes sensitive content to _config/dev.env or _config/release.env in that environment’s media bucket. A separate _config/<environment>-database-bootstrap.env contains the bootstrap login material. Those objects and Terraform state contain secrets; no secret values were read for this page.

GitHub repository/environment variables carry object URIs and role identifiers, not database passwords. The deploy role is permitted to read the matching settings object. The workflow downloads the full object into memory, streams it through SSH to release-host.sh configure, and fails on a configured-object read error. An unset URI keeps the host settings unchanged. The configure command accepts only an explicit key allowlist and writes a private 0600 file, checking the recorded configuration digest before updates.

The runtime policy covers objects throughout its own media bucket, including _config; do not present that prefix as a separately isolated secret vault. Environment isolation here is by bucket, scoped identities and selected configuration. The read-only coding role cannot retrieve these objects or read IAM policies live.

GitHub’s OIDC token is exchanged with STS for a one-hour environment deploy role. Trust includes exact repository/environment subjects, the sts.amazonaws.com audience and branch dev or main. The role reaches only its host for temporary SSH access and receives additional narrowly scoped settings/database-operation policies. Its host policy does not permit power changes or arbitrary Terraform applies.

The application’s dedicated IAM-user keys are a separate runtime mechanism because this Lightsail path does not use an EC2 instance role. They stay in private settings and supply bucket access, the allowed backup prefix and pool-scoped account deletion. OIDC removes long-lived GitHub deploy keys; it does not remove the runtime key pair.

Cost controls are alerts and bounded resources

The dev host runs continuously; the former cost-safety audit and backup-gated hibernation are retired.

The budget code defines a US$15 monthly actual-cost budget with notifications near US$10 and US$15 when recipients are configured. It has no Rewind-only cost filter, so it should not be described as an application-only spending meter. Alerts notify; they do not cap spend or stop resources.

Merged #516 removed the cost-safety audit Lambda, its failed Scheduler path and associated audit alarm/roles. Its change record says the scheduler trust was wrong, deliveries failed and the alarm had no recipients. The surviving rewind-demo-power-controller is a separate legacy component in demo/automation.tf.

The remaining controller can start the one dev host, or stop it only with a recent backup-manifest key. An optional automatic-start schedule exists only when its expression is configured; the default is null. Deploy workflows do not invoke this controller. Live Lambda/Scheduler enumeration was denied to the coding profile, so this page does not claim that an optional schedule is active.

Merged #519, resolving #512, removed backup-gated hibernation and its destroy/stop scripts. Hosted dev runs continuously with PostgreSQL/S3 data outside the host. The retained wake script is for host creation/rebuild; its latest/manifest paths are SQLite-era recovery paths.

Other controls are tangible resource choices: one small host per environment, single-AZ databases, no declared NAT/load balancer/cluster, backup/artifact expiry and pruning old image pairs. Dev’s three Lightsail status/CPU/burst alarms were observed in OK state. Their script manages them because they are outside the Terraform resources used here. CloudTrail management logging was also observed active.

Back up data separately from rebuilding compute

Managed database recovery and verified logical backups complement versioned media and source-bound application bundles.

PostgreSQL resources enable backup retention, a daily backup window and a final snapshot on deliberate deletion, with Terraform prevent_destroy. The repository documents a seven-day managed point-in-time recovery window. This is the primary database recovery mechanism, not automatic high availability.

The host’s rewind-backup.timer runs at 03:15 UTC with up to 15 minutes of random delay and catches missed runs. On PostgreSQL, backup.sh calls backup-postgres.sh: it takes a read-only TLS pg_dump, restores it into a throwaway verifier and checks row counts before upload. The configured script path is not proof that every night’s timer actually fired.

Dev and release have independent private, encrypted, versioned backup buckets and prefixes (rewind-demo/ and rewind-release/). Backup objects expire after 30 days and superseded versions after seven days. Dev deployment-artifact objects expire after three days. The runtime’s backup policy grants the configured object prefix without delete permission.

SQLite-era backups use VACUUM INTO, a media archive and a checksum/size manifest. Atomic restore verifies the artifacts in private staging before swapping files, and restores prior files on failure. That process is not the way to roll back a live PostgreSQL database. Managed restore rehearsal stops writers, compares restored table sets/counts/content hashes, and requires explicit resumption.

Application rollback restores compatible images; Terraform recreates infrastructure; database recovery restores a selected data point; S3 versioning retains object history subject to lifecycle. None implies the others. See deployment verification and rollback and database design.

Live bucket metadata, both hosts/databases, dev alarms and CloudTrail logging were inspected. Dev HTTPS health passed. Release origin HTTP was refused; its public HTTPS path, active application revision, Cognito journeys and actual database cutover remain unverified. Older release-cutover prose predates the now-existing database, so current source and these dated observations take precedence.

Questions to expect

Can rebuilding the host recover the database?
No. Terraform and cloud-init recover infrastructure and prerequisites. Data must come from the surviving managed database/S3 or an explicitly selected recovery point.
What does a successful logical backup prove?
The script verifies that its dump can restore and reconcile row counts before upload. It does not establish a universal RPO/RTO or prove the scheduled job ran every day.
What would you verify before presenting release as ready?
Public HTTPS health and revision, active database engine/schema, isolated Cognito sign-in, upload/playback and the environment’s own backup/recovery path.
