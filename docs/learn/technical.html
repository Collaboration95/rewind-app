Takeaway: the server is deliberately "stdlib + 2 packages". Most of what a framework would give you (routing, validation, auth, migrations, job queue, SSE hub) is hand-rolled.

1HTTP layer

  • createServer(...) at server/src/http.ts:3789. Routing is one giant if (pathname === … ) / pathname.match(regex) chain (~4.5k lines). No router, no middleware stack.
  • Limits are code, not config-only: JSON ≤ 64 KiB, media ≤ 50 MiB, 30 s body idle, 120 s upload, 2 concurrent intakes, 1 concurrent processor. Errors: 408 / 413 / 429.
  • Auth transport gate (authTransportIsSecure): allowed if real TLS, or loopback + localhost host + no X-Forwarded-Proto (dev only), or a trusted proxy proves HTTPS via the secret X-Rewind-Origin-Auth header that CloudFront injects. nginx hard-sets X-Forwarded-Proto: https only because CloudFront strips it.
  • No distributed rate limiter. Login/invite-guess throttles live in SQLite.

2Auth & sessions

  • Passwords: Node's built-in scrypt, params stored per row (so cost can be raised later). Unknown user → verifies against a dummy hash, so timing doesn't reveal accounts.
  • Throttle: 5 failures / 15 min window, then 15 min cooldown. Sessions: 12 h idle, 30 d absolute.
  • __Host- cookie prefix forces Secure + Path=/ + no Domain. Native/Demo path uses a bearer token; if both are sent and differ, the request is rejected (http.ts:2802).
  • Login verification and password change are queued through one promise chain (serializeAuthOperation). Works only because there is a single process.
  • Authorisation is separate: policy.ts + group-membership checks per route (cross-group-access.test.mjs exists for this).

3SQLite & migrations

  • Files: server/migrations/001…028*.sql, but db.ts (2.2k lines) holds a JS list with a key per migration, and many keys run custom JS (applyMediaProcessingMigration etc.) because SQLite can't ALTER constraints. Those rebuild tables with foreign_keys=OFF, then PRAGMA foreign_key_check.
  • Two receipts: schema_migrations(version) and schema_migration_markers(key). Health checks re-verify both, plus migrationNeedsRepair, so a half-applied migration is detected.
  • BEGIN IMMEDIATE takes the writer lock up front; the "already applied?" check is repeated inside it for concurrent starters.
  • WAL = readers don't block the writer. Several connections coexist (server, scheduler has its own schedulerDatabase, reminder loop opens its own). That's why busy_timeout matters.
  • Numbering gaps/dupes (two 006-, two 007-, no 011/012) are visible in the folder; the code comment at line 19 explains key-vs-version handling.

4Job queue (clip + film)

  • Not a separate service. server start runs the HTTP server and the cycle scheduler loop and (if configured) the reminder loop in one process (cli.ts). server worker is an optional standalone loop for jobs. (inferred) the request path also processes jobs, since routes like /contributions/jobs/:id/process exist.
  • Concurrency control is a fencing token (claim_generation): every progress/complete write checks it, so a zombie worker can't overwrite a newer claim. Classic lease + fencing pattern, in SQL.
  • Lease PROCESSING_CLAIM_LEASE_MS = 15 min. Stale reclaim "resumes the same attempt"; only pending/failed bump the attempt count.
  • Retries: film capped at 3 (QUEUE_MAX_FILM_ATTEMPTS), clip automatic cap then manual retry. Failures are bucketed: invalid_metadata / source_unavailable / processing_failed / unknown.
  • Worker polls (idle 1 s, batch window 8). No push, no LISTEN/NOTIFY (SQLite has none).
  • Cleanup jobs: retention.ts, consistency.ts (plan → apply repair, audited), staged-file cleanup.

5Media pipeline internals

  • One MediaStore interface (media/store.ts), three impls: disk, local (immutable object refs, don't extend), s3. AWS SDK is dynamic-imported at runtime (runtime-store.ts:95), so non-S3 setups never load it.
  • S3 trust model: the bucket itself enforces the checksum on PUT; the server then re-checks hash, encryption mode and version id before trusting the object. Browsers upload straight to S3, so video bytes never pass through the Node box (only the 2-concurrent-intake path for disk).
  • Reads never hand out raw S3 URLs: access token route authorises, then the server serves (with a serving budget). (inferred) this is the "locked until reveal" enforcement point.
  • ffmpeg: spawned with execFile (args array, no shell), video → libx264; photo → looped still → standard 3 s portrait clip; film → concat of normalised clips (a comment notes concat needs identical encodings, so every clip is re-encoded first).
  • Integrity layer: integrity.ts, integrity-cache.ts, backfill.ts (adds hashes to older rows at startup via backfillMediaIntegrity).

6Realtime (SSE)

  • Hub is an in-memory pub/sub, process-local. SQLite is the truth; the hub only delivers after commit. A 2nd server instance would break live delivery (no shared bus).
  • encodeSseEvent has a metadataOnly mode (ids only, no body): used for hidden/blocked content so the stream doesn't leak it.
  • Browser EventSource can't read HTTP error bodies, so the server returns a terminal SSE frame for those callers (http.ts:253). Native uses an adapter (native-event-source.ts).
  • nginx has proxy_buffering off for /api, required or SSE would stall.

7Client runtime

  • No Redux/React-Query/router in dependencies. State = React Context providers + hooks + stores written to AsyncStorage/SecureStore (inferred from deps and file names).
  • Which adapter is used is decided at startup by env: EXPO_PUBLIC_LOCAL_BASE_URL present → Runtime adapter; absent → offline Demo. Baked into the bundle at build time (EXPO_PUBLIC_* are inlined by Expo).
  • src/capture/ is the biggest client folder (19 files): state machine, interruption handling, uploader with retries, browser recorder (retro-browser.ts), looks/filters. Platform split via platform.ts.
  • Boundary rule enforced by scripts/check-architecture.mjs: regex over imports; src/domain + cycles/engine.ts can't import Expo/RN/SQLite.

8PWA, service worker, web push

  • The SW never caches or queues anything private: API, media and non-GET always hit the network (offline = a synthetic "unavailable" response). /admin is bypassed entirely (Basic-auth prompt can't be shown from a worker).
  • scripts/stamp-pwa-build.mjs rewrites sw.js per build (cache name / asset list) so a deploy invalidates the old shell; check-pwa.mjs verifies it in CI.
  • Push is outbox pattern: reminders/outbox.ts persists the intended send first, a loop delivers, so a crash doesn't lose or double-send (inferred from name and size). Notification click carries a validated {kind, groupId, reminderId} intent (strict regex in sw.js).
  • iPhone web push only works from an installed Home Screen PWA over HTTPS: why that tier needs the hosted dev URL.

9Build, container, CI, deploy

  • Container hardening: digest-pinned base images, npm ci --ignore-scripts, a script copies only production runtime deps into stage 2, npm/npx/yarn removed from the final image, uid 10001, read-only root FS, cap_drop: ALL, no-new-privileges, tmpfs /tmp, 127.0.0.1-only port binding (nginx is the only way in).
  • Supply chain: vendor/node-forge and vendor/braces are patched tarballs installed via file: (security overrides for transitive deps; tests node-forge-security, braces-security guard them).
  • Quality workflow jobs: classify change (docs-only skips) → static+root tests → server tests+coverage (installs ffmpeg) → frontend Jest with a 70% statement gate → browser (export once, PWA + a11y + responsive) → cloud-free deploy fixtures (backup/restore/lifecycle shell tests) → aggregate gate job (the one branch protection needs).
  • Deploy: deploy-dev.yml only deploys a commit that passed Quality; concurrency group is serial (cancel-in-progress: false); AWS creds via OIDC role trusting repo:…:environment:dev + refs/heads/dev.
  • Host ops scripts (deploy/): backup-manifest, restore-atomic, pause/wake, migrate-with-backup, recovery-selection, each with a shell test in tests/deploy/.
