1. INTRODUCTION

1.1 Project name and description

Project name: Rewind — Private Group Time Capsules.

Rewind is a private, invite-only group-memory concept. Members contribute
small, everyday moments during a collection cycle. The product deliberately
delays the reveal so that the group experiences the resulting capsule together
instead of immediately consuming a polished social-media feed. The selected
proposal describes four-week cycles, a five-clip/30-second weekly allowance,
retro-inspired presentation, a compiled group film, chat, reminders, and an
archive [P2].

The Sprint 1 implementation is a local-first proof of concept. It uses an Expo
client and a typed local Node service backed by SQLite. Demo members, groups,
sessions, invitations, cycles, and media metadata are synthetic/local data.
The service is not cloud hosting, and a synthetic Demo session is not secure
authentication or an account. The design preserves ports and adapters so a
later milestone can replace local storage and transport without rewriting the
domain model [P3, P5].

1.2 Problem and proposed outcome

Mainstream social media rewards immediate, curated publishing. After friends
graduate, relocate, or otherwise separate, the small unplanned moments that
maintained their connection can disappear. Rewind addresses this by making a
shared group ritual: capture a short moment, keep it sealed during the cycle,
and experience the collection later. The value is the shared memory and low
pressure to perform, not photographic perfection [P2].

For this Sprint 1 report, the meaningful outcome is narrower and demonstrable:
the project moved from a seeded walking skeleton to a locally executable
identity/group/capture boundary. A demonstrator can enter an explicitly
labelled Demo session, create or join a local group, choose a prompt, inspect
the current group/cycle state, exercise permission and capture states, review
and accept a still or bounded clip, and submit a validated local pending clip
job. The local runtime enforces session, membership, cycle-owner, media, and
idempotency boundaries. Chat, real film compilation, reveal/playback, archive,
cloud authentication, and cloud storage remain outside this increment.

1.3 Project methodology

The project uses Scrum, adapted for a small, evidence-oriented engineering
team.

- Sprint 0 produced the walking skeleton and the local runtime foundation. The
  runtime foundation was deliberately moved from Sprint 1 into Sprint 0 so
  feature work would start on a verified boundary [P3, PR #77, PR #78].
- Sprint 1 is planned as a two-week slice (13–26 September 2026 in the
  planning record). The exact reporting dates are intentionally left blank for
  the team to enter.
- Work is selected from a GitHub Project and milestone. Each issue has a
  stable orchestration key, parent epic, dependencies, risks, observable
  acceptance criteria, verification commands, and stop conditions [P3].
- The working agreement limits concurrent implementation to five active child
  issues. Dependent work is not considered Ready until its boundary and
  predecessor evidence are clear.
- The intended delivery loop is one bounded issue -> one branch -> one
  reviewable pull request -> committed synthetic/manual proof -> issue status
  Done. Peer review and automated checks are part of the Definition of Done.
- The local-first fallback is explicit. If LAN, native capture, SQLite, or
  FFmpeg is unavailable, the team may use deterministic local fixtures, but it
  must not claim multi-device capture or production privacy.

This is Scrum in practice rather than a claim that every planned ceremony or
story was completed. The repository contains planning, backlog, PR, test, and
evidence records; team meeting attendance, story-point estimates, and named
individual contributions still need to be filled in from the team’s own notes.

1.4 Project summary

The original proposal was broader than the Sprint 1 proof. Its intended
architecture is a modular monolith with a worker, PostgreSQL, private object
storage, OIDC, scheduled reminders, and a future Android/PWA delivery path.
The classroom demonstration uses a one-day cycle so the capture-to-reveal
concept can be shown without waiting four weeks [P2].

Sprint 0 and Sprint 1 consciously narrowed the active boundary to a local
Node/SQLite/Expo system. The local service provides health/version reporting,
deterministic five-member fixtures, migrations/reset, typed repositories,
membership policy, Demo sessions, audit events, group/invite mutations, cycle
control, and local media-job contracts. This boundary is valuable because it
proves domain and failure behaviour without AWS credentials, production
accounts, or private media. It also makes the remaining cloud transition
visible instead of hiding it behind an unverified mock.

8. Prove cross-group negative access and preserve safe operational diagnostics.
9. Finish the complete chat -> cycle transition -> film -> archive journey and

3.3 What was actually delivered

The merged increment is best described as “local Demo identity, group,
invitation, capture, cycle-control, and authorization foundations,” not as the
complete Rewind product. It proves the most failure-prone boundaries needed
before chat and reveal can be built:

- an acting identity is explicit and bounded;
- group and membership mutations are validated and atomic;
- cycle timing is deterministic and shared by client/server policy;
- device capability and media lifecycles are represented as states;
- accepted capture metadata is separated from transient local file URIs;
- uploads are validated, cancellable, retryable, and idempotent;
- protected routes deny cross-group access without revealing resource content;
- reset and failure paths are designed to recover without silently retaining
  stale local state; and
- all demo/simulator limitations are labelled honestly.


4. CLOSED ISSUE DEEP DIVE

4.1 Identity, groups, invitations, and diagnostics

#33 — Add safe local audit event logging
https://github.com/Collaboration95/rewind-app/issues/33

The issue required diagnosable session/job actions without private-content
logging. The implementation adds an allowlisted audit event shape containing
event type, synthetic actor ID, namespaced local resource ID, timestamp, and
success/failure/denied result. Job wrappers record started/completed/failed
events while rethrowing the original failure, so a failed job remains
correlatable without storing its exception, message body, invite code, raw
media path, or secret. `npm run server:diagnostics` exposes human-readable or
JSON local inspection. Events stay in the ignored SQLite database and are not
remote telemetry.

#34 — Define the mock-session contract
https://github.com/Collaboration95/rewind-app/issues/34

The profile picker was replaced conceptually by an explicit Demo-session
contract. A session has a stable synthetic actor, group ID, `accessKind: demo`,
start/expiry timestamps, and terminal invalidation. New sessions last eight
hours and are revalidated by the local service; expiry is not silently
extended. Missing, non-demo, expired, and invalidated sessions are denied and
do not fall back to a picker or imply secure authentication. Contract tests
cover persistence, bounded expiry, invalidation, and validation outcomes.

#35 — Sign in and sign out with Demo access (STORY)
https://github.com/Collaboration95/rewind-app/issues/35

The demonstrator can choose one of five named synthetic members, restore the
local Demo session, and deliberately leave it from Settings. The UI says
“Demo” and “synthetic” rather than “account” or “login.” Sign-out returns to a
clean Demo-entry state, and session errors remain actionable. The story is
complete as a local demonstration flow; password collection, account creation,
OIDC, and production identity remain excluded.

#36 — Create a local group and choose a prompt (STORY)
https://github.com/Collaboration95/rewind-app/issues/36

An owner can create a named local group, choose a built-in prompt or enter a
short custom prompt, and start a one-day collecting cycle. The client validates
empty/oversized values before persistence; the server commits group, owner
membership, and initial cycle atomically. Later review fixes reconcile the
session pointer if a post-commit local write fails, preventing a misleading
error followed by duplicate group creation. Owner transfer, removal,
discovery, and cloud synchronization are not part of this story.

#37 — Create an expiring local invitation code
https://github.com/Collaboration95/rewind-app/issues/37

The owner can generate and copy an eight-character uppercase code for the
current group. The code exposes bounded expiry/use state, is never written to
the audit stream, and cannot silently target another group. The contract uses a
24-hour default within a five-minute minimum and seven-day maximum; cloud
delivery, email, and public deep links are excluded.

#38 — Accept an invite and establish local membership (STORY)
https://github.com/Collaboration95/rewind-app/issues/38

An active Demo member can enter a code and join only the intended local group.
The runtime validates session, group binding, expiry, usage state, malformed
input, duplicate membership, and cross-group attempts before atomically adding
membership and consuming the code. Negative tests verify that rejected attempts
do not write membership. This proves private-group policy in the local
boundary, not cross-device identity proof.

#39 — Add account/group settings and confirmed demo reset
https://github.com/Collaboration95/rewind-app/issues/39

Settings surfaces the current synthetic actor, group, and owner/member role. It
provides group creation, sign-out, and an app-owned reset confirmation. The
confirmation names the consequence: saved Demo session, locally created
groups, local selection, accepted still metadata, and app-owned cached capture
files are removed, then the deterministic fixture returns. It does not touch
source-controlled files, migrations, remote data, or other users. Review bug
#81 hardened this flow when the local runtime rejects or is unreachable.

4.2 Capture and media boundary

#40 — Add device capability and camera permission states
https://github.com/Collaboration95/rewind-app/issues/40

The capture route distinguishes capability from permission. Camera and
microphone may be supported, unsupported, or undecided; permissions may be
granted, undetermined, denied, or blocked. The UI keeps the shutter disabled
until requirements are satisfied and provides retry/Settings guidance rather
than trapping a user. Expo SDK 57 and explicit iOS/Android usage strings form
the native boundary. The simulator fixture is deliberately separate from the
native adapter.

#41 — Record a vertical clip with audio and a 15-second cap (STORY)
https://github.com/Collaboration95/rewind-app/issues/41

The video contract accepts only portrait MP4 media with microphone audio and a
maximum duration of 15 seconds. The recording session exposes idle,
recording-with-elapsed-time, complete, cancelled, and failed states. A stop or
cancel invalidates stale async completions so an old recording cannot overwrite
a newer session. A real device is required for hardware recording; simulator
evidence is not presented as physical capture.

#42 — Review, trim, retake, and choose an original capture mode
https://github.com/Collaboration95/rewind-app/issues/42

Before submission, a member can review a bounded clip, set trim bounds inside
the recorded duration, retake/discard, and choose original Soft Focus or High
Contrast modes. Trim segments must be finite, ordered, inside the clip, and at
least 0.5 seconds. Pending metadata is persisted separately from the local
file URI. The modes are original metadata/preview choices, not copied recipes
or pixel-processing claims.

#43 — Upload local clip with validation and visible progress
https://github.com/Collaboration95/rewind-app/issues/43

The client validates session-bound MP4 input before a job is created: positive
size under 50 MB, duration over zero and no more than 15 seconds, portrait
dimensions, and audio. Upload progress has explicit validating, uploading,
complete, cancelled, and failed states. An idempotency key lets retry return
the same pending job rather than consuming quota twice; cancellation releases
the pending contribution/job. The current contract is local runtime metadata
and a temporary source, not cloud object storage or a completed film pipeline.

4.3 Cycle and authorization

#53 — Implement deterministic cycle clock and owner demo controls
https://github.com/Collaboration95/rewind-app/issues/53

One framework-independent engine calculates both one-day and four-week
windows. Tests inject a clock, validate ISO instants, calculate phases and
remaining seconds, and advance both boundaries by a positive whole number of
seconds while preserving duration. The local owner control checks persisted
owner membership before validating the requested advance and records previous
and next boundaries, actor, amount, and timestamp. The control is a demo
accelerator, not unrestricted member time travel or a production time service.

#69 — Add cross-group negative-access regression suite
https://github.com/Collaboration95/rewind-app/issues/69

The suite exercises protected group, message, contribution, clip, film, and
download categories. A member of another group receives the same safe 403
denial without resource content, and owner-only cycle control is denied outside
the intended group. Authorization is performed before resource lookup or cycle
input validation so malformed requests do not reveal whether a resource
exists. This is a strong local policy regression boundary, not a production
penetration test or security certification.

4.4 Review defects found and closed after PR #80

PR #80 received a detailed review that indexed 13 findings. Issues #81–#89
were opened for the actionable review defects and PR #91 delivered the fixes.
The review index is recorded in issue #90:
https://github.com/Collaboration95/rewind-app/issues/90

#81 — Sign-out and Demo reset cannot clear local state when runtime rejects
https://github.com/Collaboration95/rewind-app/issues/81

The original mutation wrapped remote invalidation and local clearing in one
try/catch. A runtime 404/409/unreachable response therefore kept the local
session active and skipped cleanup. The fix follows the restore policy:
401/404/409 or an unreachable local runtime are treated as “clear locally and
continue.” Reset now still removes session, group, selection, and capture data
when the runtime cannot respond, while a reachable runtime remains terminally
invalidated.

#82 — Demo cycle advance is reachable without a session
https://github.com/Collaboration95/rewind-app/issues/82

The old route fell back from missing `sessionId` to a guessable `memberId`
query parameter. A LAN caller could advance the cycle and append an event
without a validated session. The fix requires a valid session, derives the
actor only from that session, returns `401 session_required` when absent, and
regresses omitted, empty, invalid, owner, and non-owner cases. The synthetic
profile read remains intentionally public within the demo boundary, so the
correct report language is “session-protected local control,” not “secure
authentication.”

#83 — Capsule refetch churn plus review hygiene items
https://github.com/Collaboration95/rewind-app/issues/83

Three low-severity defects were closed: runtime repositories are memoized so
unrelated session-context renders do not refetch the capsule; the actor-switch
test asserts observable current-member state rather than a name that is always
listed; and the machine-specific `premium-audit.json` artifact is removed or
made reproducible. These fixes improve maintainability and test credibility
without changing capture or cycle semantics.

#84 — Offline group resolution and picker selection diverge from active session
https://github.com/Collaboration95/rewind-app/issues/84

The offline repository previously scanned local groups first and hardcoded an
owner role, so a session attached to the seeded group could display an unrelated
local group. Entry-screen member selection could also leave the selection store
on Amber while the session actor was Birch. The fix makes the session’s member
and group the source of truth, derives the role from membership, and keeps the
picker/session actor aligned.

#85 — Default web capture path cannot save a still
https://github.com/Collaboration95/rewind-app/issues/85

Expo’s legacy web file-system shim has no cache directory, so the default web
camera could take a picture but always failed while copying it to managed
storage. The fix adds a browser-local Blob-backed file store and keeps the URI
transient; durable metadata stores dimensions, format, timestamp, byte length,
and source only. Native capture continues to use the verified managed cache.

#86 — Retaking a still deletes the just-accepted metadata record
https://github.com/Collaboration95/rewind-app/issues/86

After `accept()` persisted metadata, `retake()` still cleaned the active preview
with metadata removal enabled. The fix treats accepted metadata as durable:
retake releases only the transient preview file, while discard and explicit
reset retain their cleanup semantics. This preserves the record the UI has
already promised to accept without exposing a durable URI or thumbnail.

#87 — Local runtime answers 500 for malformed path segments
https://github.com/Collaboration95/rewind-app/issues/87

Raw `decodeURIComponent` calls could throw `URIError` for malformed percent
encoding and escape into the generic 500 handler across sessions, groups,
messages, contributions, clips, films, and downloads. A shared safe decoder
maps the client error to `400 invalid_request` before resource lookup. The
issue also records a lower-severity request-body-draining hygiene note; the
closed delivery claims malformed-path handling, not a separately verified
socket-level body-drain change.

#88 — Group creation can commit without the session pointing at the new group
https://github.com/Collaboration95/rewind-app/issues/88

The runtime committed group, membership, and cycle before the client stored the
new session group pointer. If that local write failed, the user saw an error
even though the group existed, and retry could create a duplicate. The fix
reconciles the committed group/session state or makes the post-commit pointer
step non-fatal, while retaining offline rollback behaviour.

#89 — Native camera capability probe blocks capture on a physical device
https://github.com/Collaboration95/rewind-app/issues/89

`CameraView.isAvailableAsync()` was a web-only export in the installed Expo
camera version. Calling it on native threw, and the catch path parked a real
device in `capability-undecided` forever. The fix feature-detects the probe and
uses the native device boundary/permissions when the export is absent. The
explicit DemoCameraPlatform fixture remains labelled and cannot claim hardware
capture.


5. ARCHITECTURE, DESIGN PATTERNS, AND ENGINEERING PRACTICE

The following are patterns evidenced by the code and design records. They are
safe to present as “patterns applied/observed”; they should not be described as
formal GoF claims unless the team adds diagrams and a rationale section.

5.1 Ports and adapters (hexagonal boundary)

Framework-independent domain contracts sit behind adapters. The capture UI
depends on `CameraPlatform`, `CaptureFileStore`, and metadata ports instead of
Expo or a filesystem implementation. `ExpoCameraPlatform` is the native/web
adapter; `DemoCameraPlatform` is a deterministic simulator/test adapter. The
same approach is used by typed runtime repositories and the local HTTP client.
This keeps platform/device code out of domain policy and makes the local-first
boundary replaceable [rewind-app/docs/architecture/ADR-0002-camera-capture-boundary.md,
rewind-app/docs/architecture/architecture-guardrails.md].

5.2 Repository pattern

`GroupRepository`, `CycleRepository`, and runtime repository factories expose
domain-shaped reads while hiding offline fixtures, SQLite, and HTTP details.
The active session supplies the acting member and group context. Memoizing the
runtime repository objects prevents unnecessary refetches and stabilizes React
effects (#83).

5.3 Strategy/adapter selection for platform capabilities

The app selects native Expo, browser Blob, in-memory, or explicit simulator
strategies for capture/file storage. The choice allows the same capture
orchestration to run on a physical device, browser, simulator fixture, and
tests without pretending those environments have identical capabilities.

5.4 State-machine modelling

Capture, upload, Demo-session, and cycle lifecycles are represented as explicit
states and transitions rather than implicit booleans. Examples include
checking -> capability/permission result -> ready -> capturing -> preview ->
saving/saved or failure; upload validating -> uploading -> complete/cancelled/
failed; and collecting/revealing/archived cycle phases. Generation counters
prevent stale asynchronous recording/upload completions from mutating a newer
state.

5.5 Transaction and unit-of-work boundaries

Local group creation commits group, owner membership, and the initial cycle as
one SQLite mutation. Invite acceptance commits membership and invite
consumption atomically. Cycle advance updates boundaries and records a control
event in one transaction. These boundaries prevent partial state and make the
failure tests meaningful.

5.6 Command/idempotency and retryable job handling

Clip upload carries an idempotency key and returns a pending contribution/job
contract. Cancellation and retry are first-class operations. Audited job
helpers record safe started/completed/failed events while preserving thrown
failure semantics. This is the foundation for the future FFmpeg/film worker,
not evidence that the worker or cloud queue is already complete.

5.7 Policy-as-a-function and fail-closed authorization

The server centralizes member and owner decisions. Authorization runs before
resource lookup and input validation where disclosure would matter, and all
protected categories return the same safe denial shape. The architecture check
also fails closed when framework/device imports cross the domain boundary.

9. SPRINT RETROSPECTIVE DRAFT

9.1 What went well

- The team made the local-first boundary explicit. This removed cloud
  credentials and deployment setup from the critical path while retaining a
  replaceable adapter design.
- Moving #28–#32 into Sprint 0 was a useful planning correction. Sprint 1
  features could build on a typed service, SQLite, fixtures, FFmpeg preflight,
  and membership policy instead of speculative UI-only state.
- The identity/group/capture work was dependency ordered. Session state feeds
  group and cycle policy; capture ports isolate native/browser differences; and
  idempotent pending jobs provide a seam for later processing.
- Review was productive rather than ceremonial. The PR #80 review identified
  13 concrete defects, including a LAN-reachable sessionless cycle mutation,
  native capture deadlock, reset failures, metadata loss, malformed-path 500s,
  and state divergence. The defects were indexed and fixed through #81–#89 and
  PR #91.
- The app is unusually honest about evidence. The simulator fixture says that
  no physical image was captured; locked states omit media controls; Demo
  access is not called authentication; and cloud/reveal limitations are
  documented.
- Tests cover more than the happy path: invalid sessions, owner/non-owner
  controls, cross-group denials, malformed paths, invite misuse, upload
  validation/idempotency, capture cancellation, reset failure, and architecture
  import boundaries.

9.2 What could have been done better

- The original Sprint 1 goal included chat, reminders, compilation, reveal,
  archive, and a full demo runbook. The closed set stops before those features.
  The plan should have been split into a smaller “identity + capture boundary”
  sprint and a follow-up “cycle + archive” sprint.
- The aggregate delivery shape made review harder. PR #91 carried many issues
  and fixes together, while PR #92 is another broad follow-up with an open
  review index. Smaller dependency-aligned PRs would make acceptance and
  rollback easier.
- The review found defects that focused tests could have caught earlier:
  native capability feature detection, web cache behaviour, accepted-still
  retention, session/group single-source-of-truth, and group pointer
  reconciliation. Those boundaries should be added to the initial test matrix,
  not only after review.
- The plan did not record enough estimation/velocity data for a trustworthy
  burndown. Closure timestamps can show the 13 milestone issues closed on
  10–11 September, but story points, planned capacity, and ceremony time need
  team records.
- Physical-device evidence remains a risk. Simulator screens validate honest
  UI states but cannot prove native camera/microphone recording or upload.
  A real-device capture rehearsal should be scheduled before claiming the
  complete contribution flow.
- The repository experienced duplicate late Sprint 1 issues from an overlapping
  GitHub CLI operation. The duplicates are labelled and blocked, but backlog
  hygiene should be checked before the next sprint starts.
- Named team ownership and contribution percentages are not recoverable from
  the visible GitHub author data. The team should fill the contribution table
  from meeting notes, commits, reviews, and testing/evidence work.
- A lower-severity request-body-draining observation remains attached to #87.
  It did not produce a separately verified client-visible break in the merged
  evidence, but it should be either tested or explicitly deferred.

10. OTHER THINGS TO HIGHLIGHT

10.1 Local-first is a deliberate engineering decision

The project did not accidentally omit AWS or OIDC. The accepted ADR chooses a
cloud-free local prototype first so the team can learn phone operations,
storage, permissions, and state policy without credentials/cost. Cloud work is
visible in the proposal/backlog but remains blocked until the local definition
of done is credible.

10.2 Privacy and honesty are part of the product behaviour

The sealed state is not just styling. Before reveal, the UI exposes aggregate
status and text but no media URI, thumbnail, player, or share action. Durable
metadata omits file paths. Audit logs use allowlisted event/resource fields.
Demo identity is labelled synthetic, and simulator capture says that no
physical image was captured. These constraints are appropriate evidence for a
privacy-oriented group-memory product.

10.3 One-day demonstration versus four-week product concept

The same cycle engine supports a one-day classroom demo and the proposed
four-week product cycle. This is a useful design decision: acceleration changes
the window, not the policy engine or client/server timeline. The current
closed work proves control and timing; it does not yet prove a complete
cycle-to-film transition.

10.4 Design and accessibility direction

The interface uses a darkroom-inspired charcoal/paper palette, explicit warm
accent, readable system typography, text-labelled status, dashed sealed
placeholders, visible bottom navigation, and responsive phone-width layout.
Accessible labels, disabled/busy states, retry actions, and non-colour-only
locked status are part of the contract. The current screenshots show this
direction without adding media-player chrome or a generic dashboard aesthetic.

10.5 Burndown data seed

The repository does not contain story-point estimates, so no numeric burndown
should be invented. A defensible closure-count seed is:
