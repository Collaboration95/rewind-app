## Fixture ownership and preparation

Use the existing [local real-account runner](https://github.com/Collaboration95/rewind-app/blob/e82dc427cf27264baec5ed1d1b5bc42b036bac11/scripts/run-real-account-e2e.mjs#L151) from an owned checkout with its already available accepted dependencies, Firefox, FFmpeg and supported Node runtime. The inspected existing command is npm run test:real-account-e2e. It is a proposed later rehearsal command, not a command run by this documentation task. Do not install dependencies or start it against a hosted environment as part of this handoff.

The runner creates a temporary root, a disposable SQLite database/media store and its own Firefox trust profile. It checks availability of the owned localhost ports for two fresh runs, builds a web artifact with Demo disabled and /api configuration, and serves strict local HTTPS. It strips unrelated Rewind environment settings, confines the API listener to loopback and cleans up its own process/data/profile after each run. It does not change the system trust store or grant camera/microphone permissions. Do not stop another process to acquire a port or point its database/media settings at shared data.

Use only the fixture-created real accounts: first-group owner, shared invited member, distinct second-group owner and unrelated outsider. These are synthetic accounts using the actual real-account/session/membership boundaries. They are not Demo identities or real people's content. Owner/member actions occur sequentially in the fixture's browser context, not as a claim of simultaneous physical-device use. Media consists of the retained portrait H.264/AAC test clip and a generated solid-colour image. The test submits them through authenticated contribution APIs, not through physical camera capture.

The existing test explicitly launches headless Firefox and disables video/trace capture. The current runner is an automated local proof route rather than a live headed demo launcher. A presenter can narrate its accepted result and source assertions. A visible paused/headed run or recording needs separately owned preparation; do not invent a supported pause flag or imply that such a rehearsal has occurred. Any UI screenshots later reused must contain only fixture data and retain their run/build provenance.
