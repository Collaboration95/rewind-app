## Deployment defects encountered and current workaround

1. `wake-demo.sh` copies backup files into `/srv/rewind/backups` as `ubuntu`, but that directory belongs to `rewind:rewind` with mode `0770`; the script suppressed the remote error and reported a generic restore/health failure. The verified files were already staged in `/tmp`. They were installed into the protected backup directory with `sudo install -o rewind -g rewind -m 0600`, then restored through `restore.sh`; the protected recovery copy remains. The script needs a repository fix before another wake.
2. The first release build inherited the Mac's arm64 Docker platform. On the amd64 host, the runtime could not become healthy and the restore script retained its backup/rollback copy. The release was rebuilt explicitly for linux/amd64, verified, staged, and restored successfully. The builder needs an explicit target-platform check before another wake.
3. The pre-existing private operator env bound the web proxy to localhost `8080`; the distribution could not reach it. The host env was updated to the documented hosted values: web `0.0.0.0:80` and allowed browser origin `https://d3ito43l174cl7.cloudfront.net`. The runtime remained loopback-only.
4. `release-host.sh promote` rejected otherwise healthy loaded amd64 images because Docker on this host assigned image IDs that differ from the builder's manifest IDs after `docker load`. The bundle itself passed `release.py verify`; both running containers matched the host's loaded image tags, had the exact source-revision label and amd64 architecture, and both health endpoints passed. With no prior active release, the operator atomically recorded `current-release`, config version and private config digest; the failed arm64 candidate and pending pointer were quarantined rather than deleted. This image-identity check needs a portable repository fix before a future upgrade/rollback.
