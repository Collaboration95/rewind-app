# SWE5006 project brief

Status: working summary  
Last reviewed: 2026-08-24  
Primary source: SWE5006 module briefing and lecturer instructions

This document is a planning aid, not a replacement for the lecturer's
instructions. If a later official instruction conflicts with it, update this
summary.

## What the project must prove

The Practice Module group project must demonstrate competency across all four course areas:

1. Agile team practices — for example user stories, Scrum planning, test-driven development, pair programming, refactoring, and continuous integration.
2. Software analysis and design — a traceable transition from requirements/use cases to analysis and design models.
3. Software design patterns — a real design problem, candidate patterns, a justified choice, and an implementation based on the chosen design.
4. DevSecOps engineering and automation — a secure, repeatable path from source change through testing, quality/security checks, and delivery.

The project is assessed as a group project. The briefing describes a group of five and approximately 10 man-days of effort per participant; confirm the actual team and effort expectation with the lecturer.

## Required project outputs

The project should produce:

- A working system and its source-code repository.
- A project report covering business context, scope, architecture, analysis-to-design transition, use cases, design models, design patterns, database schema, and development lifecycle.
- Pipeline and test scripts, with evidence that the pipeline runs.
- A concise presentation with a clear problem-to-solution story.
- Agile evidence such as the backlog, user stories, sprint plans, burndown charts, reviews, and retrospectives.
- A high-level architecture/design specification and detailed analysis/design for the in-scope use cases.

The project report requirements state that each team member should own at least
one in-scope use case and one design problem/pattern discussion. Treat that as
a planning constraint from the beginning rather than something to add at the
end.

## What the proposal must establish

The proposal needs to make the following clear:

- Project title, sponsor if applicable, and team members.
- The context, stakeholders, and business or organisational problem.
- A general architecture; the briefing recommends a monolithic approach where appropriate.
- The in-scope use cases and explicit exclusions.
- How the project will demonstrate Agile practices, analysis and design, design patterns, well-structured code, and a DevSecOps pipeline.
- A rough work breakdown and effort estimate that fits the team.

## Quality bar for the problem

A strong project idea should have:

- A specific user group with a costly, risky, frustrating, or opaque workflow.
- A non-trivial end-to-end flow rather than only CRUD screens.
- At least one meaningful design tension, such as policy-driven decisions, state transitions, extensibility, notification orchestration, scheduling, auditability, or failure recovery.
- Observable quality attributes, such as security, maintainability, reliability, usability, traceability, or delivery speed.
- A realistic proof-of-concept boundary and accessible users, data, or credible scenarios for validation.
- A demo that makes the problem and the improvement visible in a few minutes.

Avoid selecting an idea solely because it uses an impressive technology. The technology should serve the problem and the evidence plan.
